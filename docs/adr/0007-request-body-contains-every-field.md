# Тело запроса содержит каждое поле контракта; необязательное значение — null

Клиент присылает в JSON каждое поле, объявленное в контракте запроса. Отсутствующий ключ — ошибка валидации:
400 `REQUEST_VALIDATION_FAILED`. Необязательное значение передаётся как `null`, а не пропуском ключа. Поле со
значением по умолчанию (например, visibility Wishlist) тоже присылается: значение по умолчанию выбирает клиент, а
`DEFAULT` в PostgreSQL остаётся только для прямых SQL-вставок.

Схемы входа поэтому не используют `withDecodingDefaultKey`, `withDecodingDefault` и `optionalKey`: необязательное
поле объявляется как `Schema.NullOr(…)`. Пустой текст по-прежнему нормализуется в `null` (`makeOptionalTextSchemas`).

Изменение ресурса присылает полное тело (`PUT`, как `PUT /api/users/:id`). Различать «ключа нет — не менять» и
«`null` — стереть» не нужно, потому что ключ есть всегда.

Правило уже соблюдают signup, login и `PUT /api/users/:id`. Решение владельца 2026-10-12.

## Рассмотренные варианты

- **Отсутствующий ключ = `null` или значение по умолчанию.** Отклонено: одно и то же намерение получает два
  представления, и для частичного обновления пришлось бы вводить третье правило «нет ключа — не менять».
- **`PATCH` с частичным телом.** Отклонено вместе с первым вариантом; при появлении реальной потребности решение
  пересматривается отдельным ADR.

## Последствия

- Минимальный запрос создания Wishlist содержит все поля: `{ "title": "Books", "description": null,
"occasionDate": null, "visibility": "private" }`.
- Ручные вызовы через `curl` и тесты присылают полные тела.
