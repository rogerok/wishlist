# Списки листаются keyset-пагинацией с непрозрачным курсором, который хранит всё, что задаёт порядок

Списки API отдают страницы только вперёд: `GET` с query-параметрами `sort`, `cursor`, `limit` и ответом
`{ items, nextCursor }`, где `nextCursor: null` означает конец. Номеров страниц, перехода на произвольную страницу и
`totalCount` нет. Следующая страница начинается строго после последней строки предыдущей: SQL сравнивает значения ключа
сортировки с курсором, а не пропускает N строк через `OFFSET`.

Порядок задаёт сервер: каждый список объявляет закрытый набор именованных сортировок (пресетов), клиент выбирает пресет
по имени. Последняя колонка ключа уникальна (`id`), поэтому порядок полный и строки с равными остальными значениями не
теряются между страницами.

Курсор — base64url от JSON, разбираемый Schema. Он хранит всё, что определяет порядок и набор строк: имя пресета,
значения ключа последней выданной строки и параметры вычисляемого ключа (например, дату `asOf`, относительно которой
Occasion Date делится на Upcoming и Past). Курсор не подписывается: область видимости (`WHERE owner_id = …`) сервер
применяет всегда, поэтому подделанный курсор сдвигает позицию только внутри уже разрешённых строк.

Битый курсор, курсор с недопустимым значением поля, курсор другого пресета, неизвестный query-параметр и `limit`,
не записанный цифрами как целое `1..100`, — 400 `REQUEST_VALIDATION_FAILED` с `location: "query"`: это невалидный
ввод, и клиент обрабатывает его одинаково — начинает список сначала. Значение курсора, которое дошло бы до PostgreSQL и
было бы им отвергнуто, должна отклонить Schema: иначе подделанный курсор превращается в 500.

Query маршрута, объявляющего query-параметры, разбирается строго, как тело по
[ADR-0007](./0007-request-body-contains-every-field.md); маршрут без query-Schema query не разбирает вовсе. `sort`,
`cursor` и `limit` необязательны — ADR-0007 касается тела запроса, а не query. Аутентификация выполняется до разбора
query, поэтому без Session ответ — 401 при любом query.

Решение владельца 2026-10-18.

## Рассмотренные варианты

- **`OFFSET`/номера страниц.** Отклонено: экранам Wishlist переход на произвольную страницу не нужен, а `OFFSET N`
  читает и выбрасывает N строк, и при вставке или удалении строки между запросами страницы сдвигаются — появляются
  дубли и пропуски.
- **Прозрачные параметры `afterCreatedAt`/`afterId`.** Отклонено: клиент начинает зависеть от колонок ключа, и смена
  пресета ломает API.
- **Курсор с подписью HMAC.** Отклонено, пока курсор не влияет на авторизацию; пересматривается, если в курсор попадёт
  область видимости.
- **Клиент выбирает колонку и направление.** Отклонено: произвольная колонка — риск SQL-инъекции и запрос без индекса.
- **`POST` для списков из-за длины query.** Отклонено: курсор занимает порядка сотни байт, а `GET` сохраняет
  безопасность, идемпотентность и кешируемость.
- **`asOf` вычисляется на каждой странице.** Отклонено: Upcoming Occasion Date, наступившая в полночь посреди обхода,
  переезжает в Past, и строки пропускаются или повторяются.

## Последствия

- Строка, вставленная позади курсора, в текущем обходе не появляется; строка, у которой изменилось значение ключа,
  может встретиться дважды или ни разу. Удаление строки, на которой стоит курсор, обход не ломает: курсор хранит
  значения, а не ссылку.
- Пресет с ключом из колонок использует составной индекс и переходит к курсору без чтения предыдущих строк. Пресет с
  вычисляемым ключом от параметра курсора индексом так не пользуется: PostgreSQL сортирует строки области видимости на
  каждой странице. Это допустимо для списков одного владельца.
- `asOf` берётся по UTC: для User восточнее UTC граница «сегодня» сдвинута на его смещение.
- Изменение пресета делает старые курсоры неразбираемыми; клиент получает 400 и начинает список сначала.
- Сортировка по колонке, допускающей `NULL`, через подмену на `infinity` (сравнение строк значений и индекс по выражению)
  — заготовленное решение для будущих пресетов, например цены Wishlist Item; реализуется вместе с первым таким пресетом.
