# Технические отказы логируются цепочкой тегов, а клиент получает общий 5xx без имени модуля

Технический отказ логируется ровно один раз — на HTTP-границе, где он превращается в ответ 5xx. Это одна строка
`operation.failed` с полями `kind`, `module`, `operation`, `userId`, `reason`, `errorId` и `errorChain`. Поле
`errorChain` строится обходом `cause`: из каждого звена копируются только `_tag` и строковое `operation`.

Типизированные ошибки сервиса (недоступная инфраструктура, повреждённая запись) логирует handler с `kind: failure`.
Дефекты — непредвиденные исключения, включая ошибки программиста, — перехватывает один middleware уровня API с
`kind: defect`. Он подключается последним, поэтому оборачивает каждый handler и все middleware эндпоинта. Он ловит
только дефекты: типизированные ошибки не логируются повторно, а отменённый запрос не превращается в 500.

Тексты ошибок, поля записей, имена SQL-ограничений и ошибки драйвера в лог не попадают. PostgreSQL кладёт данные
пользователя прямо в текст ошибки, например `Key (email)=(...)`. Поэтому для этих отказов намеренно не используются
`Effect.logError(message, cause)` и `Cause.pretty`, а дефект логируется без текста и stack. Исключение — локальная
отладка: при `LOG_DEFECT_DETAILS=true` и `MODE`, отличном от `production`, добавляется отдельная строка
`operation.defect.details` с полной причиной.

Клиент получает один из двух общих ответов problem+json: `INTERNAL_ERROR` (500) или `SERVICE_UNAVAILABLE` (503). Поле
`instance` — путь запроса в том виде, в каком его отправил клиент. Поле `errorId` — 32 случайных шестнадцатеричных
символа, которые сервер генерирует для этого отказа. По `errorId` из обращения клиента находится нужная строка лога.
Ответ не называет модуль: клиенту нужно знать только, поможет ли повтор запроса, а коды модулей привязали бы публичный
контракт к внутреннему устройству модулей.

## Рассмотренные варианты

- **Логировать `cause` целиком.** Отклонено: в лог утекают данные пользователя из текстов ошибок SQL-драйвера и из
  декодированных строк.
- **Логировать в сервисах или репозиториях.** Отклонено: тот же отказ залогирует каждый вызывающий код, включая тот,
  который справляется с ошибкой сам. Только HTTP-граница знает, что отказ стал ответом 5xx.
- **Один HTTP middleware для всех отказов.** Для типизированных ошибок отклонено: решение, какой `reason` соответствует
  ошибке сервиса, принадлежит handler'у модуля. Для дефектов принято: у дефекта нет типизированного сопоставления, и
  перехват не должен зависеть от того, не забыл ли его каждый handler.
- **Коды по модулям (`AUTH_INTERNAL_ERROR`, `USERS_UNAVAILABLE`, …).** Отклонено: разработчик получает из строки лога
  больше, чем из кода, а статистику для бизнеса собирают по логам сервера, а не по ответам клиентам.
- **Возвращать trace id запроса.** Отклонено: Effect строит server span по входящим заголовкам `traceparent`, `b3` и
  `x-b3-traceid`, то есть значение выбирает клиент. Заголовки B3 при этом вообще не проверяются: клиент мог записать в
  наши логи и ответ любой текст, например чужой email. Вернуться к варианту, когда `traceparent` будет ставить наш
  собственный gateway.
- **Экспорт трасс (OpenTelemetry).** Отложено до появления коллектора. Когда экспорт появится, span'ы должны следовать
  тому же правилу: записывать теги, а не тексты ошибок.

## Последствия

- У дефекта `errorChain` пустой, если только дефект не является ошибкой с тегом. Поэтому дефект разбирают по `errorId`,
  `module`, `operation` и воспроизведению, а не по тексту ошибки.
- `errorId` не связан с trace id Effect. Пока экспорта трасс нет, сопоставлять не с чем. Когда экспорт появится, связь
  даст сам Effect: его `tracerLogger` записывает каждую строку лога событием в текущий span, так что `operation.failed`
  с `errorId` окажется внутри трассы запроса, и трассу можно будет найти по `errorId`. До подключения экспорта входящие
  `traceparent`, `b3` и `x-b3-*` должен отбрасывать или выставлять наш gateway, иначе trace id и выборку трасс
  по-прежнему будет выбирать клиент.
- Флаг подробностей игнорируется, если `MODE` равен `production` или не задан. Даже если флаг по ошибке включат на
  production-сервере, ничего лишнего не напечатается.
- Vitest всегда выставляет `MODE=test`, поэтому флаг работает при локальном прогоне тестов. Тесты, которые проверяют
  отсутствие чувствительных данных, явно задают свою конфигурацию.
