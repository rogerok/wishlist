01 — Контекст

От текущего API к продукту

Backend уже имеет выбранный стек и часть auth foundation. План не начинает проект заново и не подменяет предметную работу инфраструктурной лабораторией.

Сейчас в репозитории

  • Effect Platform, Effect Schema, PostgreSQL, Kysely и Effect SQL.
  • Live API содержит health и незащищённый Users CRUD.
  • Auth contracts, таблицы, schema tests и hash-format уже частично готовы.
  • Production AuthService, handlers, repositories и cookie flow ещё не подключены.
  • Wishlist, Item, Sharing Link, Reservation, outbox и URL import отсутствуют.

Целевой первый продукт

  • User безопасно регистрируется и создаёт несколько Wishlists.
  • Private, Unlisted и Public имеют разные проверяемые правила доступа.
  • User или email-verified Guest резервирует Item без раскрытия личности.
  • PostgreSQL защищает от двойного резерва при нескольких API replicas.
  • Outbox и worker не теряют magic links и обязательные уведомления.

02 — Архитектура

Один сервис, глубокие модули

Существующая Effect-архитектура сохраняется. HTTP, use cases, persistence и side effects разделяются явными сервисами и Layer composition, но не превращаются в отдельные микросервисы без собственной причины для отказа.

Зафиксированные решения

  • Opaque server-side Sessions вместо JWT/refresh.
  • UUID для internal identity; отдельный random key для Sharing Link.
  • PostgreSQL outbox до отдельного broker.
  • At-least-once delivery и idempotent workers.
  • Containers в одном регионе; несколько API и worker replicas.
Не используем: Fastify, Zod, JWT, nanoid, browser automation и private marketplace APIs как обязательную основу.
03 — Domain model

Термины и invariants

Модель различает владельца списка, зарегистрированного дарителя и Guest. Reservation — самостоятельный lifecycle, а не boolean-флаг на Item.

Identity

User и Public Profile

Один обязательный Display Name. Login email всегда приватен. Public Profile показывает Display Name и только Public Wishlists.

Aggregate

Wishlist

Принадлежит одному User. Содержит title, optional description, non-recurring Occasion Date, visibility и единую ISO currency.

Visibility

Private / Unlisted / Public

Private видит owner. Unlisted доступен по текущей ссылке. Public дополнительно discoverable через Public Profile. Снижение visibility ротирует ссылку.

Snapshot

Wishlist Item

Title обязателен; URL, exact price, comment и image опциональны. Imported metadata только предлагает значения — User остаётся source of truth.

Access

Guest Session

Magic link подтверждает email только для одного Wishlist. Даже email существующего User остаётся Guest path, если User не вошёл.

Private holder

Reservation

Holder — ровно один User или Guest. Owner и другие посетители видят только free, reserved или reservedByMe, но не личность.

1

Главный concurrency invariant

В каждый момент на Wishlist Item существует не более одной Active Reservation. Это гарантирует PostgreSQL constraint/index, поэтому два API-инстанса не могут оба победить в гонке.

04 — Roadmap

Девять вертикальных milestones

Каждый milestone оставляет наблюдаемое работающее поведение и закрытые invariants. Следующий этап не начинается поверх известных ошибок предыдущего.

  1. 1

    Thin Session authentication

    Display Name clean cutover, password hashing, AuthService, signup/login/me/logout, cookie transport и закрытие публичного cross-User CRUD.

    РезультатAuthenticated principal и защищённая ownership boundary.
  2. 2

    Owner-only Wishlists

    Persistence, runtime schemas и CRUD для title, description, Occasion Date, visibility и Wishlist Currency. Каждая mutation scoped по owner ID.

    РезультатUser управляет несколькими приватными списками.
  3. 3

    Sharing и Public Profiles

    Public projection без email, high-entropy Sharing Link, единая visibility policy, rotation при снижении видимости.

    РезультатPrivate, Unlisted и Public доказуемо различаются.
  4. 4

    Wishlist Items без enrichment

    Manual CRUD, optional HTTPS URL, exact price в currency списка, priority sorting. Ни один read не делает outbound fetch.

    РезультатПолезный список работает без маркетплейсов и storage.
  5. 5

    Reservation state machine для Users

    Active/terminal lifecycle, holder authorization, atomic reserve, cancel, force-release и deletion transitions.

    РезультатДвойной резерв невозможен при конкурентных запросах.
  6. 6

    Guest access и transactional email

    Single-use challenges, Wishlist-scoped Guest Session, PostgreSQL outbox, отдельный worker, magic links и обязательные lifecycle emails.

    Core готовСоздать → поделиться → зарезервировать → отменить без регистрации.
  7. 7

    External-user security gate

    CSRF/origin, rate limits, enumeration resistance, password reset/change, verified email change, Session cleanup, User deletion и backup/restore.

    GateПосле него продукт можно показывать внешним пользователям.
  8. 8

    Service-owned images

    S3-compatible storage, manual upload, MIME/magic-byte/size limits, immutable assets и controlled delivery.

    РезультатОдна безопасная image boundary для upload и import.
  9. 9

    Async URL Import Preview

    Curated allowlist, restricted worker, OG/JSON-LD suggestions, manual fallback, copy-on-apply image и explicit refresh diff.

    РезультатУдобное enrichment без зависимости Item от marketplace availability.
05 — Marketplace import

Best-effort, а не обещание парсера

Исследование официальных источников меняет формулировку фичи: произвольная ссылка не равна официальному product API.

Что выяснено

Avito, Ozon и Wildberries документируют seller/account-scoped API. API для чтения произвольной публичной карточки по retail URL не найден. HTML metadata не гарантируется и может возвращать anti-bot response или timeout.

Следствие: manual fields — штатный terminal fallback, а не ошибка сервиса.

Открыть исследование и источники

Безопасный import pipeline

  1. Normalize. Только HTTPS, exact domain allowlist и разрешённый product path.
  2. Queue. API создаёт short-lived Import Preview job и возвращает 202.
  3. Fetch safely. Worker проверяет DNS/IP, redirects, timeouts, content type, bytes и decompression.
  4. Parse as untrusted. OG/JSON-LD — только предложения title, image, description и price.
  5. User applies. Выбранные поля копируются в Item snapshot; ошибки оставляют manual flow.
  6. Refresh by diff. Новый preview никогда не перезаписывает User edits молча.
06 — Scale lab

От простого к сложному

Все выбранные инфраструктурные темы остаются в плане, но получают порядок и входной критерий. Это учебная лестница, а не список технологий первого релиза.

Шаг ADB correctness

Constraints, transactions, idempotency, две API replicas.

Шаг BOutbox workers

Durable side effects, retries, claims и lag.

Шаг CObservability

Latency, pool saturation, conflicts, delivery outcomes.

Шаг DLoad tests

Сначала workload и baseline, потом оптимизация.

Шаг ECache / search

Только measured hotspot или public catalog query.

Шаг FBroker / stream

После fan-out, throughput или independent consumers.

Broker gate: PostgreSQL outbox contention, устойчивый throughput, replay, fan-out или изоляция независимых consumers. До появления этого сигнала RabbitMQ/Kafka добавляют вторую durability system, но не улучшают текущий invariant.
07 — Scope control

Что убрано и отложено

План сокращает не качество, а количество одновременно открытых границ. Отложенная фича возвращается только с собственным поведением и acceptance criteria.

Удалено из актуального замысла

  • Fastify, Zod, JWT/refresh и nanoid как обязательный стек.
  • Публичный login email и birthday у User.
  • Публичное или owner-visible имя holder.
  • Quantity и несколько Active Reservations на Item.
  • Automatic Reservation expiry.
  • Browser automation и undocumented marketplace APIs.
  • Automatic overwrite metadata и permanent hotlinks.

После первого product path

  • Images, manual upload и URL Import Preview.
  • Owner notifications, notification center и reminders.
  • Wishlist archive, rich filters и price alerts.
  • Public catalog, moderation и отдельный search engine.
  • Friends/followers и social feed.
  • Redis, broker, Kubernetes и microservices.
08 — Verification

Как проверять и что обсудить

In-memory тесты подтверждают contracts, но не cookie transport, worker recovery, object storage и multi-instance race. Для этих границ нужен реальный process-level smoke.

pnpm --filter @wishlist/api check-types
pnpm --filter @wishlist/api lint
pnpm --filter @wishlist/api test
pnpm --filter @wishlist/api build
pnpm --filter @wishlist/api db:check
Команды не запускаются механически все сразу. Каждый milestone начинает с самого узкого теста изменённого observable contract.
  1. Достаточно ли узкая boundary у Wishlist-scoped Guest Session, или Guest identity должна жить иначе?
  2. Корректно ли разделены User Session и Guest Session при совпадающем email?
  3. Хватает ли PostgreSQL outbox до появления измеренного broker gate?
  4. Нужен ли Public Wishlist уже в core или достаточно Private + Unlisted?
  5. Не слишком ли велик Milestone 6, и где провести дополнительную вертикальную границу?
  6. Какие метрики должны доказать необходимость cache, search engine или broker?
