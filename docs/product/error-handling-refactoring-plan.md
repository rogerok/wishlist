# План рефакторинга ошибок и логирования backend

Дата исходного плана: 2026-10-01. Статус на 2026-10-02: производственные изменения выполнены;
тесты auth/users handlers проходят. Итоговая проверка R.5, включая Node/PostgreSQL smoke, не завершена.

**Приоритет:** следующий обязательный блок перед дальнейшим расширением auth и продуктовыми задачами.
В [общем плане](./implementation-plan.md) это Milestone R, в [учебном roadmap](../../learning/roadmap.md) — шаги

Владелец пишет backend-код и тесты; агент помогает с разбором, ревью и проверкой поведения.

## Точка продолжения следующей сессии

**Следующий шаг — Node server с отдельной тестовой PostgreSQL в рамках R.5.**
В текущей сессии владелец явно отключил наставничество; в новой оно включается по умолчанию.
Повторно реализовывать рефакторинг не нужно.

В `apps/api/src/modules/auth/handlers/auth.handlers.test.ts` проходят шесть сценариев ошибок сервиса:

- SQL напрямую и через repository-обёртку: 500 / `AUTH_INTERNAL_ERROR`, безопасные теги причин;
- перегрузка hasher и отказ криптопримитива: 503 с различимыми `causeTag`;
- неизвестная причина типа `Error`: безопасный 500 без выдуманного `causeTag` / `sqlReason`;
- конфликт email: 409 / `USER_EMAIL_ALREADY_EXISTS`, без технического error-события.

Во всех сценариях проверены отсутствие чувствительного маркера в логах и исходном HTTP-теле,
отсутствие session cookie и `application/problem+json`. Для технических сбоев проверено ровно одно
событие `auth.operation.failed`. Приложение освобождается через `Effect.acquireRelease` в `it.effect`.

Дополнительно проходят успешный signup с 201, публичным телом и атрибутами cookie без credential
в теле/логах, production-cookie с `Secure` и отклонение лишнего `role` с 400 до выполнения signup.
Всего девять тестов, используются только фиктивные credentials.

Устаревший `auth.api.test.ts` с подставными handlers удалён. Его полезная проверка лишнего поля
перенесена на настоящий `AuthHandlersLive`; тесты login/me/logout писать при реализации маршрутов.
Текущая сборка auth получает `ModeConfig` при построении Layer, а `AuthService` — внутри запроса:
задать MODE через изолированный тестовый ConfigProvider и предоставить сервис через `HttpRouter.provideRequest`
на слое `HttpApiBuilder.layer`. Перед реализацией сверить это с текущим кодом.
Образец захвата логов — `users.handlers.test.ts`; там `UsersService` уже получается при сборке группы и
предоставляется через обычный `Layer.provide`, поэтому способ предоставления сервиса нельзя копировать механически.

## Выполнено и проверено в этой сессии

- Безопасные проекции `toUserFailureLog` и `toAuthFailureLog` выводят разрешённые теги, не сырой `cause`.
  В auth списки известных тегов проверяются через `satisfies` по `SignupOperationError['_tag']`.
  Общая политика реализована локальными проекциями; универсальный модуль для разных ошибок не вводился.
- `mapUsersRepositoryError` применяется во всех пяти операциях: `SqlError` с `isRetryable=true` даёт
  `UsersUnavailableError`, остальные причины — `UsersInternalError`; вся repository-обёртка сохраняется в `cause`.
- HTTP-контракты включают 500/503, в том числе DELETE. `makeTechnicalErrorHandler` централизует перевод
  технических ошибок, а контекст операции задаётся один раз. PUT `instance` и DELETE `reason` исправлены.
- Проверка перед коммитами 2026-10-02: совместный Vitest auth/users handlers — 2 файла, 10 passed
  (9 auth и 1 users). Lint всех изменённых TypeScript-файлов: 0 ошибок,
  8 предупреждений `sonarjs/no-nested-functions` в production handlers. Тестовые файлы — без замечаний.
  Отдельный HTTP smoke-прогон вне Vitest подтвердил 400 с `payload.role`, ноль выполнений signup,
  отсутствие cookie и технических ошибок. Ранее отдельно проверены шесть сценариев ошибок.
  Временные файлы удалены; PostgreSQL и сетевой сервер в этих проверках не использовались.
- Последний `pnpm --filter @wishlist/api check-types` прошёл без диагностик.
- Диагностические HTTP-запуски с настоящими handlers и подставленными зависимостями прошли:
  11 технических сценариев users, 7 сценариев auth, 7 сценариев users для 400/404/409.
  Проверены статусы, категории, отсутствие чувствительного маркера; 400 не вызывает repository,
  ожидаемые 404/409 не создают техническое error-событие.
- `users.handlers.test.ts` проверен текущим Vitest run: невосстановимый SQL-сбой даёт 500 /
  `USERS_INTERNAL_ERROR`, полезные теги причин и отсутствие чувствительного маркера в логах и ответе.
  Полный API suite не запускался.

**Осталось:** применимые общие проверки, реальный Node server с отдельной тестовой PostgreSQL
и успешным health/signup/cookie, затем сверка оставшихся auth-задач.
Результаты диагностических запусков не доказывают работу настоящей БД. Самостоятельное освоение отдельно не оценивалось.

## Цель и границы

Сделать технические сбои различимыми и безопасными в логах, согласовать их HTTP-классификацию и устранить
повторение правил, которое уже привело к ошибкам в `users`.

Сохранить разделение repository → service → HTTP. Ошибка хранилища, смысл сбоя для операции приложения
и публичный ответ — разные контракты, даже когда классы имеют похожую форму.

Входят:

- безопасная диагностика ошибок `users` и `auth`;
- согласованная классификация SQL-сбоев без добавления автоматических повторов;
- исправление `reason` у DELETE и `instance` у PUT;
- локальное устранение повторов перевода технических ошибок;
- проверки настоящих обработчиков и сервисов через существующие Layer-интерфейсы.

Не входят:

- универсальный `AppError`, общий CRUD-фреймворк или фабрика всех HTTP-ошибок;
- изменение auth-сценариев, схемы БД, лимитов хеширования и правил отмены;
- добавление retry, метрик, трассировки, request ID или новых production-зависимостей;
- унификация всех непредвиденных сбоев в Problem Details;
- механическое сокращение одинаковых строк, если за ними стоят разные правила.

## Основание: ревью 2026-10-01

| Наблюдение                                                                   | Место                                                                             | Последствие                                                                  |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| В лог передаётся весь объект ошибки                                          | `apps/api/src/modules/users/handlers/users.handlers.ts`, `logFailure`             | PostgreSQL `detail` может раскрывать значения полей записи                   |
| Лог содержит только верхний тег `AuthInternalError` / `AuthUnavailableError` | `apps/api/src/modules/auth/handlers/auth.handlers.ts`, `logFailure` и `catchTags` | Разные первопричины становятся неразличимы                                   |
| Любой `UsersRepositoryError` становится `UsersUnavailableError`              | `apps/api/src/modules/users/service/users.service.ts`                             | Постоянные ошибки кода/конфигурации получают 503 вместо внутренней категории |
| DELETE пишет `reason=dataIntegrity` при `UsersUnavailableError`              | `apps/api/src/modules/users/handlers/users.handlers.ts`                           | Лог неверно классифицирует недоступность                                     |
| PUT использует путь коллекции в технических ответах                          | `apps/api/src/modules/users/handlers/users.handlers.ts`                           | `instance` теряет адрес конкретного пользователя                             |

Проверено диагностическими запусками через настоящий `AppApiLive`, обработчики и `UsersServiceLive` с
подставленными отказами зависимостей, без рабочей БД. SQL-причина с синтетическим email в `detail` попала в лог,
но не в HTTP-ответ; две разные причины auth дали одинаковые логи; невосстановимая SQL-ошибка дала users 503;
ошибки DELETE и PUT воспроизведены. Это не проверка полного приложения с PostgreSQL.

Отдельно: `Effect.die` дал пустой 500 и запись стандартного HTTP-логгера со стеком на уровне INFO.
Текущий тест кодирования ответа допускает не-Problem-ответ. В этом блоке сохраняем такое поведение:
типизированная ошибка (failure), непредвиденный сбой (defect) и отмена (interruption) не объединяются.
Ошибка Schema на невалидном поле не раскрыла остальные поля строки; утверждать, что любой SchemaError
сейчас печатает всю запись, оснований нет.

## Порядок работы

### R.1 — Зафиксировать политику и воспроизводимые сценарии

- [ ] Сверить перечисленные места с текущим кодом и установленной версией Effect перед изменениями.
- [ ] Зафиксировать конечную таблицу: исходная причина → категория сервиса → HTTP-статус → безопасные поля лога.
- [ ] Добавить адресные регрессионные сценарии для найденных дефектов, используя реальные сервисы и обработчики.
      Подменять зависимости в точке отказа, а не сам HTTP-перевод.
- [x] Удалить устаревший `auth.api.test.ts`, сохранив полезную проверку валидации в тесте настоящего handler.
      Не восстанавливать тесты, которые лишь подставляют готовую HTTP-ошибку и проверяют её сериализацию.

**Готово, когда:** дефекты воспроизводятся, ожидаемое поведение явно определено; тесты проверяют статус,
категорию причины, адрес ресурса и отсутствие чувствительных значений, а не текст сообщений и внутреннее устройство
helper.

### R.2 — Сделать логи безопасными и диагностически полезными

- [x] Реализовать безопасные диагностические проекции локально в `users` и `auth` по одной политике разрешённых полей.
      Проекции не назначают HTTP-статус; универсальный обработчик ошибок модулей не вводится.
- [ ] Разрешить только необходимые поля: тег ошибки сервиса, известный тег нижележащей причины, операция,
      SQL `reason._tag`/код и при необходимости имя ограничения. Неизвестную причину обозначать категорией без сырого
      содержимого.
- [x] Убрать передачу необработанного `cause` в лог `users`; в `auth` сохранить различие причин до HTTP-преобразования.
- [ ] Не выводить произвольные `message`, `detail`, SQL-параметры, вход Schema, email/имена, пароли, хеши,
      credentials, дайджесты, cookies и Authorization. Диагностические строки не считать безопасными только потому, что это
      строки.
- [ ] Сохранять внутреннюю цепочку причин при переводе между repository и service; ограничивать именно вывод,
      а не уничтожать исходную ошибку раньше обработки.
- [ ] Логировать техническую ошибку один раз на HTTP-границе. Не добавлять такое же сообщение в repository/service.
      Отдельный журнал HTTP-запросов остаётся.

**Готово, когда:** перегрузка хеширования, отказ криптопримитива и SQL-сбой различимы; синтетические чувствительные
значения отсутствуют в захваченных логах и HTTP-ответах; ожидаемые 400/404/409 не превращены в error-события приложения.

### R.3 — Согласовать классификацию технических ошибок

- [x] Разделить временную недоступность и внутренний SQL-сбой в `users`, учитывая существующий `mapSignupSqlError` в

- [ ] Явно зафиксировать принятую политику для `ConnectionError`, `AuthenticationError`, `AuthorizationError`,
      `SqlSyntaxError`, известных конфликтов и неизвестных SQL-причин. `isRetryable` — сигнал для политики, не
      автоматический HTTP-статус.
- [x] Предусмотреть внутреннюю ошибку сервиса для SQL-сбоев: не называть ошибку синтаксиса повреждением пользовательской
      записи.
- [x] Обновить объединения ошибок и все затронутые HTTP-контракты/обработчики, включая DELETE, если у него появляется 500.
- [x] Сохранить обработку известных конфликтов email как 409 и отсутствие пользователя как 404.
- [x] Устранить повторяющуюся классификацию внутри `users`; общий SQL-классификатор выделять только там,

**Готово, когда:** временный отказ соединения даёт 503, ошибка SQL/прав/конфигурации — 500 по согласованной таблице;
цепочка причин сохранена, обработаны все варианты типизированных ошибок, неожиданные сбои и отмена не замаскированы под 503.

## Отложенные решения

Локальные помощники декодирования строк и оборачивания repository-ошибок допустимы, если уменьшают повторение правил;
образец уже есть в `sesion.repository.ts`. Это не обязательный массовый рефакторинг всех repositories.
Объединение admission/work semaphore-кода hasher, универсальный формат непредвиденных 500 и новые средства наблюдаемости
не блокируют этот план и требуют отдельного обоснования.
