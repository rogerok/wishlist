# Wishlist — дизайн фронтенда

Интерактивный дизайн, переработанный по Hallmark и обратной связи владельца 2026-10-22. Направление «С любовью»: праздник, щедрость, любовь, тепло и уют. Это не подключённое приложение и не новый контракт бэкенда. Имена, желания, цены, адреса и ссылки — демонстрационные. Продуктовое состояние живёт в памяти вкладки; сохраняется только предпочтение цветовой темы.

## Открыть

Откройте `docs/design/index.html` обычным браузером. Все ресурсы локальные; интернет и сборка не нужны. Для проверки clipboard и просмотра по HTTP из корня репозитория:

```sh
python3 -m http.server 4178 --bind 127.0.0.1
```

Адрес: `http://127.0.0.1:4178/docs/design/index.html`.

Верхняя панель переключает экран и тему. Пульт демонстрационных экранов в приложение не переносить; **выбор темы сохранить**, разместив его в шапке или настройках, доступных также гостю. Система описана в корневом `design.md`. Ссылки `example.com` обозначают поле source URL, не наличие товара.

## Замысел

Личный каталог желаний, а не магазин и не панель аналитики. Главные действия: создать вишлист → добавить желание → поделиться → выбрать подарок. Никаких выдуманных статистик, рейтингов, друзей, корзины, оплаты или рекламного лендинга.

Hallmark: **custom / «С любовью» / Compact collection**. Почти белая бумага, чернильный текст и красный акцент в светлой теме; глубокий чернильно-ягодный фон и ягодные акценты в тёмной. Компактная верхняя навигация, одноколоночная коллекция, обычные интерфейсные заголовки, дата и доступ в строке метаданных. Одна локальная гарнитура Golos Text во всём интерфейсе, включая логотип.

В проходе `quiet-gifts-4` убраны повторяющиеся красные CTA, дубли доступности и подвал с инструментами прототипа. Название желания теперь идёт перед приоритетом; цена и ссылка сгруппированы. «Я подарю» — контурная кнопка с иконкой; чужая бронь — текст, а не текст плюс disabled-кнопка. Посетителю не показывается лишняя строка «Желания / Сначала то, чего особенно хочется». Пояснение приватности сокращено до факта. Цвета переведены в OKLCH, без новой декоративной темы.

### Пройти основной сценарий

1. Мои вишлисты → «Создать вишлист». По умолчанию «Только мне».
2. На новом вишлисте → «Добавить желание». Сохранить идею вручную; необязательные поля можно пропустить.
3. «Поделиться» → изменить доступ → сохранить. Снова открыть sharing и скопировать ссылку.
4. Для содержательного примера переключиться на «Вишлист · посетитель» и открыть `birthday`: «Я подарю» меняет статус только после демонстрационного подтверждения.
5. Переключиться на владельца: статус есть, личности дарителя нет. Снять бронь можно только через подтверждение.
6. «Вишлист · гость» → выбрать свободный подарок → ввести вымышленную почту → «Получить ссылку» → «Имитировать переход». Настоящего письма нет.
7. Обновить страницу, чтобы вернуть исходные примеры.

Импорт: в форме желания заполнить HTTPS URL → «Предпросмотр по ссылке» → отметить предлагаемые поля → применить. Если после предпросмотра изменить ручное поле, прототип откажется затирать правку. Кнопка сбоя показывает, что ручная форма остаётся доступной.

## Правила данных и поведения

### Аккаунт и аутентификация

- User: `{ id, displayName, email }`; login/signup возвращают его напрямую, не `{ user, token }`.
- Cookie `wishlist_session`: HttpOnly, SameSite=Lax, Path=/api, срок 7 дней; Secure в production. JS не читает credential, не кладёт его в localStorage. Восстановление — `/api/auth/me`.
- При разных origins следовать фактическим CORS/deployment-настройкам, передавать cookie через credentials. PATCH пока отсутствует в CORS (`apps/api/src/server.ts:13–21`), как и подключённый Account endpoint.
- Display Name: trim, 1–100 символов. Email приватен, не редактируется этой формой.
- Пароль: точный allowlist и 8–100 символов в `apps/api/src/modules/auth/schemas/password/password.schema.ts:10–17`; нужны a–z, A–Z, цифра и спецсимвол. Login использует ту же Schema. Сверять правила с API, не усиливать их самостоятельно.
- Login 401: одно сообщение «Неверная почта или пароль», без раскрытия существования User. Signup 409: отдельное сообщение о занятой почте.
- Logout завершает только предъявленный сеанс. На технической ошибке нельзя показывать гарантированный успешный выход. Демо-кнопка показывает только успешную ветку, без сетевого вызова.
- Account change требует собственный self-service endpoint. Не заменять его `PUT /api/users/:id`. Каркас Account response `{ displayName }` расходится с целевым User response в change; контракт нужно завершить до интеграции.

### Вишлист, дата и пагинация

- Create payload содержит **все четыре ключа**: `{ title, description, occasionDate, visibility }`. Пустое необязательное значение — `null`, не пропущенный ключ. `ownerId`, id, timestamps клиент не задаёт.
- Title: trim, 1–255; description: trim, ≤1000, пустое → null. Источник: `openspec/specs/wishlists/spec.md:7–36,83–169`, ADR-0007.
- Occasion Date: неповторяющаяся календарная дата `YYYY-MM-DD`, относится к вишлисту. Отображать без сдвига часового пояса.
- Окно входа: [сегодня UTC − 1 день; сегодня UTC + 5 календарных лет], включительно. Прошедшая сохранённая дата не закрывает список. При редактировании неизменившуюся старую дату не отклонять. В прототипе «сегодня» зафиксировано на 22.10.2026 для воспроизводимых экранов; в приложении так не делать.
- Default sort: `createdAt DESC, id DESC`. `occasionDate`: сегодня/будущие по возрастанию → прошедшие от недавних → без даты; tie-breaker id ASC, `asOf` UTC фиксирован на первой странице.
- Список: `{ items, nextCursor }`, limit по умолчанию 20, 1–100; только вперёд. CTA «Показать ещё» отсутствует при `nextCursor: null`. Нет totalCount, номеров страниц, серверного «назад», поиска и неоговорённых фильтров. В прототипе первая порция — 3 примера **только для демонстрации**.
- При смене sort сбрасывать cursor и накопленные страницы. Невалидный cursor → предложить загрузить список сначала. Не обещать snapshot/live-синхронизацию.
- Private доступен только владельцу. Чужой private и отсутствующий Wishlist выглядят одинаково: «Вишлист недоступен». Не раскрывать причину 404.
- Unlisted отсутствует в Public Profile. Public появляется там. Уменьшение видимости и явная ротация инвалидируют старую Sharing Link; при переходе в private новой ссылки нет. Сама смена видимости не обещает отменить брони.

### Желания и бронирование

- Title, optional HTTPS URL, Item Price, priority, comment. Priority: `high / medium / low`, default medium. Нет quantity, ручного ранжирования или общей валюты Wishlist.
- Цена — точная строка суммы + валюта конкретного Item. Отображение демонстрации использует `Intl.NumberFormat`, не образец арифметики денег для production. В API и persistence сохранить точность без float.
- Roadmap задаёт RUB/EUR/USD и максимум 1 000 000. Точные precision/minimum, длины title/comment ещё не утверждены. Ограничение двух десятичных знаков в демо-форме — **дизайнерское предположение**, не контракт. Перед разработкой уточнить в спецификации.
- Default order: priority DESC и стабильное создание. Общую сортировку цен не рисуем: правило сравнения разных валют ещё не решено.
- Изображений нет в основном дизайне: они отнесены к отдельному milestone. Коллекция не использует обложки или декоративный номер; дата и доступ берутся из самого Wishlist.
- Отдельные проекции: owner видит статус, visitor — свободен/занят, holder дополнительно — «Вы дарите». Никакой личности дарителя в owner/visitor responses, DOM, accessibility labels и аналитике.
- Резервирует другой User через свою Session, без письма; Guest подтверждает почту для конкретного Wishlist. До подтверждения письмо не занимает подарок. Даже email существующего User не делает magic link входом в Account.
- Reservation не имеет автоистечения. Сеанс может истечь — это не освобождает подарок. Не рисовать countdown.
- В production показывать успех только после атомарного ответа сервера; уникальность обеспечивает БД. При конфликте вернуть «Этот подарок уже выбрали», не скрыть ошибку оптимистичным успехом.
- Отмена своей брони, force-release владельцем и удаление имеют разные причины завершения. В демо все опасные действия подтверждаются; обязательные по плану — force-release и delete Wishlist с активными Reservations. Владелец никогда не узнаёт держателя из подтверждения.
- Уведомления держателям планирует сервер. Не добавлять владельцу письма reserve/cancel, центр уведомлений и напоминания о поводе: они вне выбранного объёма.

### Import Preview

Асинхронный best-effort, не обязательная часть ручного создания. Production: allowlist HTTPS → enqueue → ожидание/polling → предложение → выбор полей → copy в пользовательский snapshot. Явные pending/unsupported/failed/expired состояния, без выдуманного SLA. Изображения только через сервисное хранение на соответствующем этапе.

Прототип показывает выбор полей, конфликт ручной правки и сбой; **не** выполняет extraction, polling, проверку магазинов или SSRF-защиту. Нет live sync, тихого overwrite и обещания поддержки любой ссылки. Для обновления предпросмотра production должен показывать diff и не стирать изменённые пользователем значения.

Опасная использует собственные error/hover/ink tokens. Восемь образцов показывают один вариант основной кнопки; сетка не сжимает её текст |

### Переключение темы

- «По системе / Светлая / Тёмная» доступны на каждом экране, включая гостевой просмотр.
- `theme.js` выполняется в `<head>` **до CSS**: применяет сохранённый выбор или `prefers-color-scheme` до первого стилизованного кадра.
- Ключ storage: `wishlist-design-theme`, значения `system / light / dark`. Никаких паролей, cookie credential или продуктовых данных в storage.
- Режим «По системе» реагирует на изменение настройки ОС без перезагрузки. Явный выбор пользователя имеет приоритет.
- Смена темы меняет атрибут корневого элемента, не вызывает render и не стирает черновик формы или открытый диалог.
- При запрете storage переключение продолжает работать в текущей вкладке. Сохранение между открытиями тогда не гарантируется.
- Тема меняет общую палитру и состояния, но не композицию. Нет светлых бирок на тёмных обложках: сами обложки удалены.

### Состояния и доступность

- Восемь образцов кнопки в `#states`: default, hover, focus, active, disabled, loading, error, success.
- Hover только для fine pointer; все действия доступны касанием и клавиатурой. Нет скрытого hover-only управления.
- Focus-visible: заметное кольцо; errors привязаны к полям через aria-describedby/aria-invalid. Native required и browser validation используются только для демонстрации, не заменяют серверный Schema.
- Изменение состояния объявляется в `role=status`; ошибки — `role=alert`. Dialog удерживает фокус. Skip link ведёт к main.
- Успех виден в изменившемся состоянии, не в праздничном toast. Copy меняет надпись на «Скопировано»; при запрете clipboard предлагает выделить ссылку.
- 500/503 используют безопасный код обращения `errorId`, без SQL/сырой причины/PII. При неясном результате изменения сначала перечитать данные, не предлагать слепой повтор POST.
- Клиентские ошибки раскладывать по `errors: [{ location, path, message }]` из `apps/api/src/infra/errors/request-validation.ts`. Не переводить сырую technical error в текст интерфейса.
- Входы в auth 401/409/503 доступны через «Демо-состояния формы» на экране входа/регистрации.

## Как переносить в реальный фронтенд

1. Не копировать глобальный mutable state и HTML-строки из `prototype.js` в production. Это сценарный пульт дизайна, не архитектурный шаблон и не слой авторизации.
2. Начать с компонентов AppShell/PublicShell, Button/IconButton, FormField, VisibilityPicker, WishlistCard, ItemCard, Notice, EmptyState, Dialog. Не создавать workspace package только ради токенов.
3. Сохранить семантику и desktop/mobile правила `styles.css`. Использовать фактический стек будущего frontend; этот пакет его не выбирает.
4. Сначала подключить auth и create/read Wishlist. Для прочих действий показывать недоступность либо включать их только после готового endpoint, не оставлять fake success.
5. Согласовать недостающие HTTP-контракты в соответствующих changes. Не придумывать URL и request/response из hash-маршрутов прототипа.
6. На интеграции проверить настоящую cookie-session, ошибки 400/401/404/409/500/503 и конкурентную бронь с PostgreSQL. Клиентское скрытие кнопки не является проверкой доступа.
7. Не переносить пульт экранов, демо-ошибки, фиксированное «сегодня», example.com-ссылки и примеры данных. Переключение темы, обе палитры и системный режим — **часть целевого интерфейса**, не временная демонстрация.

- 17 экранов/состояний × 12 ширин (320, 375, 414, 639, 640, 641, 768, 1023, 1024, 1280, 1440, 1920 px) × 2 темы = **408 комбинаций**. - На девяти основных экранах при 375 px измерены **285 текстовых узлов и значений/placeholder полей в каждой теме**. Минимум: **5.02:1 в светлой**, **7.24:1 в тёмной**.
