Сначала состояние, потом Effect

Цель: без кода предсказать, какие записи и credentials появляются или исчезают при signup, login, me и logout.

Три разных состояния

User
публичный профиль
1 → 1
Password Credential
доказательство личности
User
публичный профиль
1 → N
Session
временная аутентификация клиента

Password Credential и Session напрямую не связаны. Во время login Credential только доказывает, какому User принадлежит запрос. После успешной проверки создаётся новая Session с userId. В следующих запросах browser предъявляет Session credential, а сервер связывает его digest непосредственно с User.

Ключевое различие: password hash защищает низкоэнтропийный человеческий секрет медленным scrypt. Session digest индексирует высокоэнтропийный случайный token быстрым SHA-256.

Effect здесь пока не магия: каждый use case — описание перехода состояния плюс три пути завершения: success, typed failure и interruption/defect. Layers только поставляют зависимости, необходимые переходу.

Проверка понимания

После второго login с другого браузера сколько Sessions должно остаться?
Что должно остаться после ошибки между User insert и Credential insert?
Что делает `/me`, если Session существует, но `expiresAt == now`?

Практика перед Phase 1

  1. Нарисуй на бумаге таблицы User, Password Credential, Session как три коробки.
  2. Для каждого endpoint нарисуй стрелки read/write и подпиши rollback boundary.
  3. Объясни вслух: почему logout удаляет Session, но не User и не Password Credential.
  4. Открой Phase 1 дорожной карты и реализуй только Schema-контракты.

Основной manual: Pilcrow Auth Book: Sessions, затем Auth sessions. Читай переходы состояния и security-инварианты, не копируй rolling expiration или id.secret. Справочник: OWASP Session Management, разделы Session ID Properties и Session Expiration.

Урок завершён, если: ты можешь без подсказки предсказать строки БД и HTTP-ответ для success/failure каждого endpoint. Если любое место неясно — спроси агента именно про этот переход состояния.

Не переходи к hashing, пока HTTP contract не заморожен: иначе несколько неизвестных смешаются в одной ошибке.
