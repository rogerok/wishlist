Проблема: одна операция уже дорогая

Для согласованной стартовой конфигурации scrypt N=2^17, r=8, p=1 нижняя оценка рабочей памяти выражается как 128 × N × r — примерно 128 MiB на одну операцию. Это не полный RSS процесса: реализация, buffers и runtime добавляют overhead.

Что реально делает Node.js

JavaScript-код выполняется на event loop, но асинхронный crypto.scrypt() передаёт работу в фиксированный libuv thread pool. Поэтому вызов не блокирует event loop так, как scryptSync(), но занимает worker thread и память.

По документации Node thread pool также обслуживает другие async crypto operations, часть filesystem API, dns.lookup() и zlib. Если scrypt заполнит pool, unrelated операции получат дополнительную задержку.

Увеличение UV_THREADPOOL_SIZE не решает memory safety. Больше worker threads может увеличить число одновременно работающих memory-hard операций и ухудшить OOM-риск. Значение задаётся до запуска процесса и выбирается только после измерений.

Отдельный процесс не обязателен для первой версии. Он полезен, если нужна fault/memory isolation или отдельное масштабирование hashing workers. Даже отдельный процесс всё равно должен иметь лимит конкурентности и недолговечную in-memory очередь; password нельзя класть в долговечную внешнюю очередь.

Три защиты решают разные задачи

МеханизмЧто ограничиваетЧего не делает
Rate limiterСколько запросов допускается к дорогой операцииНе ограничивает конкурентность уже допущенных запросов
Effect SemaphoreСколько hash/verify Effect выполняются одновременно в одном процессеСам по себе не ограничивает длину очереди ожидающих fibers
Bounded wait/admissionСколько запросов и как долго могут ждать permitНе защищает от распределённого перебора без rate limit

В установленном Effect `4.0.0-rc.108` базовая форма:

const semaphore = yield* Semaphore.make(maxConcurrentHashes)

const boundedHash = semaphore.withPermits(1)(hashEffect)

withPermits возвращает permit после success, typed failure или interruption. Но если входящих запросов больше, чем система способна обработать, fibers будут ждать. Поэтому добавь timeout/ограничение admission и возвращай явную overload-ошибку, а не накапливай бесконечную очередь.

Начальное значение concurrency не берётся из статьи. Выбери его из memory budget и benchmark. Например, при 512 MiB доступной памяти четыре операции по 128 MiB уже исчерпывают теоретический бюджет без учёта Node/PostgreSQL/overhead — значит реальный лимит обязан быть ниже.

Rate limiting вокруг hashing endpoints

Rate limit ставится до expensive hashing. Он защищает одновременно от online password guessing и resource-exhaustion DoS. Но один ключ не закрывает все атаки:

EndpointОсновные ключиПочему
SignupIP/network + normalized emailUser ещё не существует; нужен предел массового создания и hash workload
LoginNormalized account identifier + IP/networkAccount key против rotating IP; IP key против password spraying по множеству accounts
Password changeAuthenticated user/session + IPПроверяется старый password и хешируется новый
Password reset submitReset subject/token + IPХешируется новый password; request-token endpoint может иметь другую цену

Учебный token-bucket старт для login:

capacity: 5 attempts
refill:   1 attempt / minute
key:      normalized account identifier
plus:     отдельный IP/network bucket

Bucket допускает короткий burst из пяти попыток и затем устойчиво одну попытку в минуту. Теоретический максимум одного непрерывно расходуемого bucket — около 525 600 попыток в год. Это только оценка online rate, а не доказательство безопасности «среднего пароля»: пользовательские пароли распределены неравномерно, атакующий может менять accounts/IP, а offline cracking после утечки БД вообще не проходит через rate limiter.

Не создавай account-lockout DoS. Жёсткий account bucket позволяет атакующему намеренно блокировать чужой login. Нужны короткое ожидание/постепенное замедление, несколько сигналов, generic response и наблюдаемость. Точные значения должны быть конфигурацией и результатом load/security тестов.

Порядок обработки login

  1. Нормализовать email и проверить request Schema.
  2. Проверить account/IP rate limits; превышение даёт 429 с одинаковой публичной формой для существующего и неизвестного email.
  3. Пройти bounded admission к PasswordHasher; overload инфраструктуры не маскировать под invalid credentials.
  4. Получить semaphore permit.
  5. Выполнить real scrypt verify либо совместимый dummy verify для неизвестного email, когда этот P0 hardening включён.
  6. Освободить permit автоматически при любом exit path.
  7. Только после успешной проверки создать Session.

В multi-process deployment каждый Node process имеет собственный libuv pool и собственный semaphore. Поэтому общий предел равен примерно replicas × permits. Distributed rate limiter и суммарный memory budget проектируются отдельно.
