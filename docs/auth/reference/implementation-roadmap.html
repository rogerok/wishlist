Читать: Effect v4 Quickstart, затем HttpApi Handlers. Смотреть в коде: Effect rc.108 HttpApi source и локальный modules/users. Все ограничения и файлы.

Порядок реализации

  1. Выписать таблицу endpoint: method, path, request, success status/body, error status/body.
  2. Создать password input Schema отдельно от Password Credential. Она проверяет длину 8–100, требует lowercase/uppercase ASCII letter, digit и разрешённый special character, не делает trim и отвергает whitespace.
  3. Собрать signup body из обязательных ключей email, password, passwordConfirm, firstName, lastName и middleName. Значения имён допускают string | null; отсутствующий ключ не нормализуется в null. Переиспользовать локальный UserEmailSchema.
  4. Описать login body, public User response и четыре группы Problem Details ошибок.
  5. Собрать auth HttpApi group без handler implementation. Убедиться, что API сам кодирует 201/200/204.
  6. Добавить boundary tests: 7/8/100/101 символов, отсутствие каждой обязательной категории, whitespace, password confirmation, обязательные name keys, excess property и malformed email.

3Построить security primitives

ВходPassword и random bytes
ВыходPasswordHasher и SessionTokenGenerator
Не делатьDB lookup и HTTP
Читать: Auth Book: Sessions, Node 25 scrypt, OWASP scrypt. Разобрать: pinned Lucia single-file example только как набор инвариантов.
Обязательный урок перед реализацией: bounded password hashing. Async scrypt использует libuv worker pool, но не ограничивает память и конкурентность автоматически. Определи memory budget, process-local Semaphore, bounded wait и overload behavior.

Порядок реализации

  1. Спроектировать versioned password-hash format: algorithm, version, N/r/p, salt, key.
  2. Обернуть callback-based async crypto.scrypt в отменяемый Effect; не использовать sync API.
  3. Задать N=2^17,r=8,p=1, достаточный maxmem и измерить latency/RAM на текущей машине.
  4. Измерить один hash/verify и выбранную конкурентность; оценить суммарную память как concurrency × memory per hash.
  5. Ограничить активные hash/verify через Effect Semaphore; отдельно ограничить очередь/время ожидания, потому что Semaphore сам не ограничивает число ожидающих fibers.
  6. Разделить malformed stored format и password mismatch: первое — integrity error, второе — нормальный false.
  7. Генерировать 32 random bytes, отдавать base64url token и отдельно SHA-256 digest исходных bytes.
  8. Скрывать секреты через Redacted, но раскрывать только внутри минимальной crypto/cookie границы.
ТестИнвариант
Один password дваждыРазные salt/hash, оба verify=true
Wrong passwordverify=false, не defect
Malformed hashTyped integrity failure
Token sample32 bytes, stable digest, no raw logging

Готово, когда: primitives тестируются без PostgreSQL и HTTP; production generator не детерминирован; test Layer детерминирован; benchmark обосновывает concurrency; тест доказывает освобождение permit при success, failure и interruption.

5Собрать первый вертикальный срез: signup

Состояние доEmail свободен, строк нет
Состояние послеUser + Credential + Session
FailureПолный rollback
Читать: PostgreSQL Transactions и Effect Handlers. Gap: готового Effect 4/PostgreSQL atomic-signup walkthrough нет; transaction owner выводится из локального use case.

Use case по шагам

  1. Handler принимает уже декодированный body и вызывает один AuthService.signup.
  2. Service хеширует password и генерирует Session credential до либо внутри транзакции; решение должно учитывать удержание DB connection.
  3. SqlClient.withTransaction оборачивает три inserts на одном transaction context.
  4. Duplicate email превращается в typed domain error; неизвестный SQL error остаётся unavailable/integrity.
  5. Service возвращает public User и redacted raw token. Он не знает Set-Cookie.
  6. Handler регистрирует cookie только после успешного завершения service Effect.

Эксперимент: искусственно уронить вставку Credential после вставки User. Проверить БД и отсутствие Set-Cookie. Это главный тест транзакционной границы.

Готово, когда: реальный запрос signup создаёт три согласованные строки и cookie; повтор email даёт 409; induced failure не оставляет User.

6Добавить login

ВходEmail + password
SuccessНовая независимая Session
Public failureОдин generic 401
Читать: Auth Book: Passwords и OWASP Authentication Responses. Сравнить: Better Auth sign-in/session tests для test matrix, но не копировать rolling Session и raw-token storage.
До production: login и остальные hashing endpoints получают account/IP rate limits до scrypt. Учебный старт — token bucket capacity 5, refill 1/minute — является гипотезой для load/security теста, не гарантией стойкости пароля. Подробности и границы — в уроке 2.
  1. Нормализовать email тем же Schema, что использует signup.
  2. Загрузить минимальный credential record; не возвращать его наружу AuthService.
  3. Асинхронно проверить password. Не превращать mismatch в defect.
  4. Схлопнуть unknown email и mismatch в один публичный InvalidCredentials.
  5. На каждый успех создать новую Session; не переиспользовать cookie из request.
  6. Вернуть public User и новый redacted token; handler выставляет тот же cookie contract.
СценарийНаблюдение
Unknown emailТот же status/content-type/body, что wrong password
Два loginДва разных digest, обе Sessions валидны
Broken stored hash500 integrity, не 401

Готово, когда: контракт не раскрывает существование email, а две сессии одного User живут независимо.

8Идемпотентный logout

ВходOptional cookie
Состояние послеCurrent Session отсутствует
Ответ204 + expired cookie
Читать: Auth Book: Auth sessions и MDN Set-Cookie. Сравнить: Better Auth и express-session sign-out/destroy tests как counterexamples к локальной failure policy.
  1. Не использовать required middleware: отсутствие cookie у logout является успешным no-op.
  2. Для well-formed token вычислить digest и удалить только matching row.
  3. Missing, malformed, unknown и уже удалённая Session дают 204.
  4. Если DB operation для well-formed credential падает, вернуть 503: отзыв не доказан.
  5. В ответе вызвать expireCookie с теми же name/path/domain attributes.
  6. Проверить две Sessions: logout первой не меняет вторую.

Не путать: removeCookie редактирует создаваемый response, но не удаляет cookie из браузера. Нужен expiry header.

Готово, когда: последовательность logout → logout остаётся 204, первая Session даёт 401, вторая — 200, cookie jar удаляет credential.
