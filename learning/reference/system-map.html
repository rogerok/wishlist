1. Сборка при старте: граф Layer

Процесс запускает server.ts. Каждый Layer создаётся один раз и отдаёт сервис тем, кто его требует. Стрелка значит «нуждается в».

flowchart TB
  server["server.ts — запуск процесса"] --> http["HttpLive — Node HTTP сервер, CORS"]
  server --> app["AppServicesLive — app.ts"]
  http --> api["AppApiLive — HttpApiBuilder, RequestValidation и DefectBoundary middleware"]
  api --> hh["HealthApiLive"]
  api --> uh["UsersHandlersLive"]
  api --> ah["AuthHandlersLive"]
  api --> wh["WishlistsHandlersLive"]
  app --> um["UsersModuleLive — UsersService + UsersRepository"]
  app --> am["AuthModuleLive — AuthService, 3 репозитория, PasswordHasher, TokenGenerator"]
  app --> wm["WishlistsModuleLive — WishlistsService + WishlistRepository"]
  uh -. "UsersService" .-> um
  ah -. "AuthService" .-> am
  wh -. "WishlistsService" .-> wm
  um --> db["DBLive — Kysely + CamelCasePlugin"]
  am --> db
  wm --> db
  db --> pg["PgClientLive — пул соединений PostgreSQL"]

Пунктир: handler получает сервис из Context. Связь появляется в server.ts: HttpLive.pipe(Layer.provide(AppServicesLive)).

Почему это важно. Код внутри конструктора Layer выполняется один раз. Если там вызвать randomBytes, все запросы получат одни и те же байты. Код внутри функции сервиса выполняется на каждый вызов.

2. Один запрос: POST /api/auth/signup

sequenceDiagram
  autonumber
  participant C as Клиент
  participant H as HttpApi
  participant AH as AuthHandlers
  participant S as AuthService
  participant X as Hasher и TokenGenerator
  participant DB as PostgreSQL
  C->>H: POST /api/auth/signup, JSON
  H->>H: Schema проверяет payload
  alt payload невалиден
    H-->>C: 400 Problem Details, handler не вызван
  end
  H->>AH: payload
  AH->>S: signup без passwordConfirm
  S->>X: hash пароля, новый token
  X-->>S: passwordHash, credential, digest
  Note over S,X: вне транзакции — scrypt не держит соединение
  S->>DB: BEGIN
  S->>DB: INSERT users
  S->>DB: INSERT password_credentials
  S->>DB: INSERT sessions с token_digest
  S->>DB: COMMIT
  S-->>AH: user, credential, expiresAt
  AH-->>C: 201, тело UserResponse, Set-Cookie HttpOnly

В БД попадает только digest токена. Сам credential уходит клиенту в cookie и больше нигде не хранится.

Вход работает. /me проходит через middleware SessionAuthentication: он вызывает authenticate и кладёт CurrentSession в Context — урок 0004. Выход (POST /api/auth/logout) читает cookie сам, без middleware, и всегда истекает её при 204 — разбор logout.

3. Wishlist: create и read под Session

Оба маршрута защищены middleware SessionAuthentication. Владелец и читатель берутся только из CurrentSession: ни тело, ни query их не выбирают.

sequenceDiagram
  autonumber
  participant C as Клиент
  participant H as HttpApi
  participant WH as WishlistsHandlers
  participant R as WishlistRepository
  participant DB as PostgreSQL
  C->>H: POST /api/wishlists, cookie, JSON
  H->>H: SessionAuthentication
  alt Session нет или истекла
    H-->>C: 401, instance — путь без query
  end
  H->>H: Schema payload, окно даты по Clock
  alt тело невалидно или лишний ключ
    H-->>C: 400 REQUEST_VALIDATION_FAILED
  end
  H->>WH: payload и CurrentSession
  WH->>R: create(user.id, input) через service
  R->>DB: INSERT 4 поля и owner_id явно
  DB-->>R: строка с id и timestamps
  R-->>WH: Wishlist после decode строки
  WH-->>C: 201, JSON из 8 полей, ISO timestamps

Окно Occasion Date — UTC [сегодня − 1 день, сегодня + 5 лет] — проверяет SchemaGetter.checkEffect при каждом запросе (wishlist.schema.ts). Тело содержит каждый ключ, лишний ключ — 400: ADR-0007.

sequenceDiagram
  autonumber
  participant C as Клиент B
  participant WH as WishlistsHandlers
  participant S as WishlistsService
  participant DB as PostgreSQL
  C->>WH: GET /api/wishlists/:id, cookie B
  WH->>S: getReadableById(B, id)
  S->>DB: SELECT WHERE id AND (owner_id = B OR visibility = public)
  alt строка найдена
    DB-->>S: строка
    S-->>C: 200, JSON из 8 полей
  else чужой Private или id нет
    DB-->>S: пусто
    S-->>C: 404 WISHLIST_NOT_FOUND, одно тело
  end

Правило доступа живёт в одном SQL, поэтому скрытый и отсутствующий Wishlist неразличимы: тела 404 совпадают полностью. Технический отказ — 503 или 500 по ADR-0005; повреждённая строка не исправляется при чтении, а даёт 500.

5. Таблицы

erDiagram
  users ||--o| password_credentials : "пароль"
  users ||--o{ sessions : "сессии"
  users ||--o{ wishlists : "владелец"
  users {
    uuid id PK
    varchar email "уникален без учёта регистра"
    varchar display_name "без крайних пробелов"
    roles role
  }
  password_credentials {
    uuid user_id PK, FK
    text password_hash "scrypt v1"
  }
  sessions {
    uuid id PK
    uuid user_id FK
    bytea token_digest "32 байта, уникален"
    timestamptz expires_at
  }
  wishlists {
    uuid id PK
    uuid owner_id FK
    varchar title "1-255, не пустой после btrim"
    varchar description "NULL или 1-1000"
    date occasion_date "NULL или дата без времени"
    visibility visibility "private или public"
  }

Все FK — ON DELETE CASCADE: удаление user удаляет его пароль, сессии и Wishlist. Миграции: 0001, 0002, 0003, 0004.

Два правила БД. occasion_date — тип date: драйвер возвращает строку YYYY-MM-DD, без превращения в момент времени, поэтому часовой пояс процесса её не сдвигает (pg-date.test.ts). Миграции идут только вперёд: обратных нет, локальная БД пересоздаётся.

Проверь себя

В signup-запросе нет ключа middleName. На каком шаге диаграммы запроса он остановится и с каким статусом?

Шаг 2: Schema отклонит тело запроса, клиент получит 400. Handler и сервис не вызываются, поэтому строк в БД нет.

Почему транзакция открывается в AuthService, а не в handler?

Транзакция — часть сценария «создать user, пароль и сессию вместе». Сценарий живёт в service. Handler знает только HTTP: статусы, cookie, логи.

Пользователя удалили. Что стало с его сессиями и почему?

Удалены: sessions.user_id ссылается на users с ON DELETE CASCADE. Это делает PostgreSQL, а не код приложения.

B запрашивает чужой Private Wishlist. Почему ответ 404, а не 403?

403 сказал бы B, что такой id существует. SQL читает строку только при owner_id = B или public, поэтому чужой Private и несуществующий id дают одно и то же пустое Option и одинаковое тело 404.
