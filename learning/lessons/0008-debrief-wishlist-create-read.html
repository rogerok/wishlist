1. Окно даты проверяет decode запроса и читает Clock на каждом запросе

Чтоwishlist.schema.ts:39–51 и тест wishlists.handlers.test.ts:857–877:

export const CalendarDateInWindow = CalendarDate.pipe(
  Schema.decode({
    decode: SchemaGetter.checkEffect((value: string) =>
      Effect.gen(function* () {
        const { min, max } = occasionDateWindow(yield* DateTime.now);
        return (value >= min && value <= max) || `Expected a date between ${min} and ${max}`;
// тест: тот же payload, меняются только часы
const accepted = yield* postWishlist(app, owner.cookie, body);       // 2026-10-12 → 201
yield* TestClock.setTime(Date.parse('2026-10-13T12:00:00Z'));
const rejected = yield* postWishlist(app, owner.cookie, body);       // 2026-10-13 → 400

ПочемуЕсли окно вычислить один раз при старте, сервер, запущенный 12 октября, 20 октября примет 2026-10-11 с ответом 201 вместо 400. Тест с двумя разными датами при одних часах этого не заметит: при старте и при запросе время одно. Поэтому в тесте меняются только часы. Без Clock в контексте handlers падают ровно 4 теста окна.

Сохранённая Schema окна не знает. Иначе Wishlist с 2020-02-29, созданный год назад, при чтении дал бы 500 вместо 200 — сценарий «Чтение старой Occasion Date».

ЦенаDecode стал эффектом, зависящим от Clock. Тест HTTP обязан донести свои часы до handlers: acquireApp кладёт Clock в их контекст, а слой БД собран на настоящих часах (excludeTestServices), иначе прыжок setTime задевает таймеры пула и тест зависает.

Окно вычислили один раз при старте сервера 12 октября. 20 октября клиент отправляет occasionDate: "2026-10-11". Какой статус он получит и какой тест это поймает?

201 вместо 400: окно застыло на 12 октября. Падает тест «окно сдвигается вместе с Clock между запросами»: после сдвига часов он ждёт 400. Решение 1.

2. Правило доступа — в одном SQL, поэтому скрытый и отсутствующий Wishlist неразличимы

Чтоwishlists.repository.ts:75–89 и тест wishlists.handlers.test.ts:719–734:

.selectFrom('wishlists').selectAll()
.where('id', '=', id)
.where((eb) => eb.or([eb('ownerId', '=', viewerId), eb('visibility', '=', 'public')]))
// тест: 404 на чужой Private, затем DELETE этой строки и снова GET
expect(yield* readJson(missing)).toEqual(hiddenBody);

ПочемуАльтернатива — прочитать строку по id, а владельца проверить в service. Тогда чужой Private даёт 403, а пустой id — 404. B перебирает id и по статусу узнаёт, какие Wishlist существуют. Один SQL возвращает пустой результат в обоих случаях, и service строит одно тело 404 с тем же id и instance. Тест удаляет строку и сравнивает тела целиком.

ЦенаНи клиент, ни лог не отличают «нет доступа» от «нет строки»: владелец, отлаживая доступ B, видит только 404. Новое правило доступа (шаг 4, sharing) меняет условие в SQL, а не if в service.

Service переделали: SELECT по id, затем «owner ≠ viewer и private → 403». Что узнает B, запросив чужой id, и какой тест упадёт?

B узнает, что Wishlist с этим id существует и закрыт: 403 против 404 у пустого id. Падают «Чужой Private Wishlist» и «Одинаковое тело 404 для одного id». Решение 2.

3. Строгий разбор задают настройки AppApi; Schema сама лишний ключ отбрасывает

Чтоinfra/api/api.ts:12 и create-wishlist.schema.test.ts:108–117:

// api.ts — действует на все группы, собранные через HttpApiBuilder.group(AppApi, …)
.annotate(HttpApi.PayloadParseOptions, requestParseOptions)
// тест Schema — вне HttpApi настройки передаются в decode вручную
Schema.decodeUnknownEffect(CreateWishlistBodySchema, requestParseOptions)(body)

ПочемуБез настроек Schema молча выбрасывает лишний ownerId: POST отвечает 201, и клиент думает, что выбрал владельца. По ADR-0007 такой запрос — 400. Мутации: убрать аннотацию с AppApi — падают 5 HTTP-тестов серверных полей; убрать второй аргумент decode — падают 5 тестов Schema. Аннотация на тестовом HttpApi не действовала вовсе: handlers читают настройки того API, что передан в group (HttpApiBuilder.js:313 в effect 4.0.4). Её убрали из шести тестов.

ЦенаТест Schema без второго аргумента выглядит правильным и проходит на допустимых телах — забыть его легко. Настройка одна на весь AppApi: endpoint, которому нужно терпеть лишние ключи, потребует своей аннотации на группе или endpoint.

В тесте Schema убрали второй аргумент decode. Что вернёт decode тела с лишним ownerId? Какой статус даст HTTP-запрос с тем же телом?

Decode вернёт успех без ownerId: ключ отброшен молча. HTTP по-прежнему даст 400: настройки берутся из аннотации AppApi, а не из теста. Решение 3.
