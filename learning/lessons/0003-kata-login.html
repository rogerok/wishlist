Это обычный тестовый файл проекта. До реализации login общий запуск тестов намеренно будет красным. Текущие результаты — в STATE.md.

Порядок твоей работы

  1. Поиск по email. В UsersRepository пока есть только getById. Добавь getByEmail по его образцу: точный поиск, Option, декодирование и перевод ошибок. Не загружай всех пользователей. Добавь соответствующую операцию и тип ошибки; в ошибке невалидной строки используй её row.id.
  2. Контракт сервиса. В auth.service.errors.ts добавь ошибку неверных credentials и тип ошибок login. В login.schema.ts опиши вход сервиса и результат с User, credential и expiresAt, как у signup.
  3. Операция login. В AuthService найди User, загрузи Password Credential и вызови hasher.verify. При неверных credentials не создавай Session. При успехе сгенерируй новый token, сохрани digest и верни результат. Не превращай SQL-сбой или повреждённый hash в ошибку неверного пароля.
  4. HTTP. Подключи существующее описание login в auth.api.ts. Добавь обработчик в auth.handlers.ts: вызов сервиса, перевод ошибок, cookie и только User в теле.
  5. Зависимые тесты. После добавления метода в интерфейс компилятор покажет неполные подмены сервисов, например в auth.handlers.test.ts. Обнови их явно; не делай login необязательным ради старых тестов.
flowchart TD
  request[POST /api/auth/login] --> user[Найти User по email]
  user -->|Нет User| denied[401 без новой Session]
  user -->|Есть User| credential[Загрузить Password Credential]
  credential --> verify[Проверить пароль через hasher.verify]
  verify -->|false| denied
  verify -->|true| token[Сгенерировать новый token и digest]
  token --> session[Сохранить новую Session]
  session --> response[200: User в теле, token в cookie]

Это успешный путь и ожидаемые отказы. Технические ошибки проходят отдельный перевод в 500/503 по существующей политике.

1. Проверяем настоящий обработчик, не готовый ответ

Чтоauth.login.test.ts:29–32 собирает настоящие зависимости.

const servicesLayer = Layer.mergeAll(
  AuthModuleLive,
  SessionRepositoryLive,
).pipe(Layer.provideMerge(databaseLayer));

ПочемуПодставленный результат login не обнаружит пропущенную проверку пароля или отсутствие записи Session. Здесь HTTP-запрос проходит через настоящий AuthService.

ЦенаНужны Docker, PostgreSQL и реальные вычисления scrypt. Тесты выполняются медленнее проверки с подменами.

Если login всегда принимает любой пароль, какой сценарий обнаружит ошибку?

Сценарий неверного пароля потребует 401 и неизменность сессий. Решение 1.

2. Проверяем связь cookie с сохранённой сессией

Чтоauth.login.test.ts:98–109 извлекает token и вычисляет digest от исходных bytes.

digest: createHash('sha256')
  .update(Buffer.from(credential, 'base64url'))
  .digest(),

ПочемуСлучайная cookie сама по себе не доказывает существование Session. Тест ищет Session по digest и сверяет её владельца и срок.

ЦенаПроверка знает публичный контракт token: base64url и SHA-256 от декодированных bytes. При смене этого контракта тест тоже изменится.

Login выдал новую cookie, но ничего не записал в sessions. Что обнаружит тест?

Поиск по digest вернёт None вместо Session. Одного статуса 200 для прохождения недостаточно. Решение 2.

3. Освобождаем и приложение, и данные теста

Чтоauth.login.test.ts:65–71 регистрирует освобождение HTTP-приложения.

return yield* Effect.acquireRelease(
  Effect.sync(() => makeApp(auth, mode)),
  (app) => Effect.promise(() => app.dispose()),
);

Помощник register отдельно удаляет тестового User при завершении scope. Внешние ключи удаляют его credentials и сессии.

ПочемуПосле проваленной проверки следующий тест должен снова зарегистрировать тот же email, а не получить 409 из-за чужих данных.

ЦенаОсвобождение ресурсов описано явно. Контейнер остаётся общим для группы, но данные каждого зарегистрированного User очищаются.

Проверка статуса упала после успешного signup. Удалится ли тестовый User?

Да: acquireRelease зарегистрировал удаление в scope теста. Ошибка проверки не пропускает освобождение. Решение 3.

Границы каты

Четыре теста покрывают основные сценарии login. Они не доказывают все технические отказы, устойчивость к перебору, одинаковое время ответа или работу браузера.

При подключении login сохрани действующую политику ошибок и безопасных логов. Маршруты me/logout, rate limit и изменения схемы БД в эту задачу не входят.
