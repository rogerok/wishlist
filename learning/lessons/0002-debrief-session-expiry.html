Сессия перестаёт находиться точно в момент expiresAt

Ты добавил условие срока в repository. Агент добавил тест перехода через границу. Разберём три решения в этой проверке.

Repository Регрессионный тест Карта системы

1. Тест проверяет точный момент истечения

Чтоsession.repository.test.ts:40–47: часы переходят через срок с шагом 1 мс.

yield* TestClock.setTime(expiresAt.getTime() - 1);
expect(yield* lookup).toBeOptionSome(session);

yield* TestClock.setTime(expiresAt.getTime());
expect(yield* lookup).toBeOptionNone();

yield* TestClock.setTime(expiresAt.getTime() + 1);
expect(yield* lookup).toBeOptionNone();

ПочемуПроверка только до и после срока не отличает > от >=. Равенство должно давать None.

ЦенаТест фиксирует точность до миллисекунды. В PostgreSQL столбец имеет тип timestamp(3), а часы приложения возвращают миллисекунды.

stateDiagram-v2
  state "Поиск возвращает Some(session)" as valid
  state "Поиск возвращает None" as expired
  [*] --> valid: now меньше expiresAt
  valid --> expired: now достигает expiresAt
  expired --> expired: now больше expiresAt

Это изменение результата поиска, а не удаление строки. Просроченная сессия может оставаться в таблице.

Если заменить > на >=, какой из трёх случаев сломается?

Точное равенство: запрос вернёт сессию вместо None. Решение 1.

2. Один Effect запускается при разном времени

Чтоsession.repository.test.ts:37–41: описание поиска создаётся до установки времени.

const session = yield* repo.create(userId, digest, expiresAt);
const lookup = repo.getByTokenDigest(digest);

yield* TestClock.setTime(expiresAt.getTime() - 1);
expect(yield* lookup).toBeOptionSome(session);

Почемуlookup хранит описание вычисления, а не найденную сессию. Каждый yield* lookup снова читает Clock и выполняет запрос.

Если сохранить время при создании Layer, все три запуска будут сравнивать срок с одним старым значением. Тест обнаружит это.

ЦенаТест выполняет три запроса к настоящей PostgreSQL. Это проверяет результат SQL-фильтра, а не только сравнение двух чисел.

Часы перешли за expiresAt. Нужно ли заново вызывать getByTokenDigest, если lookup уже создан?

Нет. Повторный yield* lookup заново прочитает Clock внутри Effect.gen. Решение 2.

3. Новые часы принадлежат только этому тесту

Чтоsession.repository.test.ts:46–48: тест получает собственный экземпляр часов.

  yield* TestClock.setTime(expiresAt.getTime() + 1);
  expect(yield* lookup).toBeOptionNone();
}).pipe(Effect.provide(TestClock.layer())),

ПочемуВ первой версии агент сдвинул общие часы группы layer(repoLayer). Два соседних теста получили None вместо живой сессии.

Отдельный TestClock.layer() не меняет часы соседних тестов. Контейнер PostgreSQL при этом остаётся общим для группы.

ЦенаУ теста появляется отдельный Layer часов. TestClock управляет временем Effect, но не now() PostgreSQL.

Поэтому тест создаёт сессию со сроком завтра, чтобы выполнить ограничение БД expires_at > created_at. Затем он перемещает только часы приложения.

Тест перевёл TestClock на завтра. Переведётся ли время PostgreSQL и соседних тестов?

Нет. PostgreSQL использует собственные часы, а локальный Layer изолирует часы этого теста. Решение 3.

Источники и границы проверки

Контракт auth требует, чтобы expiresAt был позже текущего времени приложения.

TestClock установленной версии Effect описывает setTime и layer().

Эта проверка относится к repository. Она не доказывает работу HTTP-аутентификации /me, которая ещё не реализована.
