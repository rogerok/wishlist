Урок · keyset-пагинация · 10 минут

Следующая страница начинается строго после последней показанной строки, а не через N строк

Разберём четыре шага keyset на списке Session одного User, а потом те же шаги появятся в модуле пагинации с пропусками для тебя.

ADR-0008 design.md Карта системы

Данные примера

У User пять Session. s3 и s4 созданы в одну и ту же миллисекунду — для timestamptz(3) это обычное дело. Сортировка: новые сверху, страница — 2 строки.

flowchart LR
  s5["s5 · 10:00:05"] --> s4["s4 · 10:00:03"]
  s4 --> s3["s3 · 10:00:03"]
  s3 --> s2["s2 · 10:00:02"]
  s2 --> s1["s1 · 10:00:01"]
  s4 -. "курсор после страницы 1: (10:00:03, s4)" .-> s3
  s2 -. "курсор после страницы 2: (10:00:02, s2)" .-> s1

Порядок задаёт пара (created_at, id). Курсор — это значения пары у последней строки страницы.

Разобранный пример: страница Session

Код запускался на PostgreSQL из тестов проекта (TestDatabaseLive), запрос пишется через тот же DB, что в репозиториях.

const listSessions = (userId: string, cursor: SessionCursor | undefined, limit: number) =>
  Effect.gen(function* () {
    const db = yield* DB;

    const rows = yield* db
      .selectFrom('sessions')
      .select(['id', 'createdAt'])
      .where('userId', '=', userId)
      // 1. Отрезать уже показанное
      .$if(cursor !== undefined, (query) =>
        query.where((eb) =>
          eb(eb.refTuple('createdAt', 'id'), '<', eb.tuple(cursor!.createdAt, cursor!.id)),
        ),
      )
      // 2. Упорядочить тем же ключом, что в WHERE
      .orderBy('createdAt', 'desc')
      .orderBy('id', 'desc')
      // 3. Взять на одну строку больше страницы
      .limit(limit + 1);

    // 4. Собрать страницу: первые limit строк, курсор — по последней из них
    const items = rows.slice(0, limit);
    const last = items.at(-1);
    const nextCursor = rows.length > limit && last !== undefined
      ? { createdAt: last.createdAt, id: last.id }
      : null;

    return { items, nextCursor };
  });
  1. Отрезать уже показанное. (created_at, id) < (10:00:03, s4) — сравнение строк значений: сначала по created_at, при равенстве по id. Для порядка «новые сверху» «после курсора» значит «меньше». Для порядка по возрастанию знак был бы >.
  2. Упорядочить тем же ключом. ORDER BY обязан совпадать с WHERE по колонкам и направлению. Иначе «после курсора» в WHERE и «следующие» в выдаче — разные множества строк.
  3. Взять на одну строку больше. Пришло limit + 1 строк — следующая страница точно есть. Пришло меньше — эта страница последняя. COUNT(*) не нужен.
  4. Собрать страницу. Клиент получает первые limit строк. Курсор строится по последней выданной строке, а лишняя строка только сообщает «есть продолжение».

Вывод запуска, limit = 2:

страница 1: s5, s4; nextCursor s4
страница 2: s3, s2; nextCursor s2
страница 3: s1;     nextCursor null

Каждая Session выдана ровно один раз, s3 и s4 с одинаковым временем разошлись по разным страницам без потерь.

Предсказание

Уберём id из ключа: WHERE created_at < курсор.createdAt и ORDER BY created_at DESC. Остальное то же. Что получит клиент на страницах при тех же пяти Session?

Сначала ответь в чате, потом открой 
страница 1: s5, s3; nextCursor s3
страница 2: s2, s1; nextCursor null

s4 не попала ни на одну страницу. Без id PostgreSQL вправе выдать s3 и s4 в любом порядке и выбрал s3. Курсор стал 10:00:03, а условие created_at < 10:00:03 отрезало всё время 10:00:03 — вместе с ещё не показанной s4. Ошибки нет, строка просто молча пропала. Поэтому последний элемент ключа — уникальный id (тай-брейкер).

Что из этого станет модулем

У Wishlist две сортировки, а у будущих списков их будет больше. Шаги 1–4 одинаковы для любой сортировки, различается только ключ. Поэтому модуль infra/pagination/keyset.ts получает сортировку как описание:

  • направление: 'asc' или 'desc';
  • ключ над колонками строки — для ORDER BY и левой части WHERE;
  • ключ над значениями курсора — для правой части WHERE;
  • как построить курсор из последнего элемента.

Шаги 1–4 модуль выполняет сам. В следующем шаге ты заполнишь в нём шаг 1 и шаг 4.

Сортировка по возрастанию, курсор стоит на строке (2026-12-31, id₇). Какой знак в WHERE и почему?

>: при порядке по возрастанию следующие строки больше курсора. Знак выводится из направления, а не пишется вручную в каждом списке.

Источник

Markus Winand, «We need tool support for keyset pagination» — почему OFFSET медленнее с каждой страницей и как сравнение строк значений использует индекс.
