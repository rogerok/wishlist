Страница списка — это один SELECT с условием «после курсора», а курсор — это ключ последней показанной строки, упакованный в строку

Пройдём один запрос GET /api/wishlists от клиента до PostgreSQL и обратно, разложим, какой файл за что отвечает, и составим маршрут, по которому ты напишешь модуль с нуля.

Урок 0010: четыре шага keyset design.md Карта системы

1. Что видит клиент

У User три Wishlist. Клиент просит страницы по 2. Endpoint появится в задаче 5.2, но форма ответа уже закреплена Schema makePageSchema (infra/pagination/page.ts).

GET /api/wishlists?limit=2
→ 200 { "items": [W3, W2], "nextCursor": "eyJzb3J0IjoiY3JlYXRlZEF0IiwiY3JlYXRlZEF0IjoiMjAyNi0xMC0xOVQxMDowMDowMy4wMDBaIiwiaWQiOiI0YzFk…" }

GET /api/wishlists?limit=2&cursor=eyJzb3J0Ijoi…
→ 200 { "items": [W1], "nextCursor": null }

Курсор только выглядит загадочно. Это base64url от JSON. Тот же курсор, раскодированный (вывод запуска makeCursorCodec из проекта):

{"sort":"createdAt","createdAt":"2026-10-19T10:00:03.000Z","id":"4c1d2e3f-0a1b-4c2d-8e3f-112233445566"}

Внутри три вещи: какой сортировкой выдан курсор и значения ключа (createdAt, id) у последней строки страницы, то есть у W2. Клиент не читает и не собирает курсор. Он только возвращает строку, которую получил (ADR-0008: «непрозрачный курсор»).

nextCursor: null — единственный признак последней страницы. Ни total, ни номера страницы в ответе нет.

3. Что уходит в PostgreSQL

Вывод .compile() того же запроса с CamelCasePlugin, как в DBLive. Первая страница, курсора нет:

select "id", "title", "created_at" from "wishlists"
where "owner_id" = $1
order by "created_at" desc, "id" desc
limit $2                                   -- $2 = 3, то есть limit + 1

Вторая страница, курсор стоит на W2:

select "id", "title", "created_at" from "wishlists"
where "owner_id" = $1
  and ("created_at", "id") < ($2::timestamptz, $3::uuid)   -- после курсора
order by "created_at" desc, "id" desc
limit $4                                   -- $4 = 3
  • where "owner_id" = $1 пишет repository. Это область видимости, keyset её не трогает.
  • ("created_at", "id") < (…) — сравнение строк значений: сначала по created_at, при равенстве по id. Знак < следует из desc, для asc был бы >.
  • ::timestamptz и ::uuid сообщают PostgreSQL тип параметра. Без них вычисляемый ключ occasionDate падает с could not determine data type of parameter (design, решение 5).
  • Индекс (owner_id, created_at DESC, id DESC) из миграции 0005 совпадает с этим порядком, поэтому PostgreSQL может сразу перейти к курсору, а не читать предыдущие строки.

4. Зачем модуль, а не одна функция в repository

У Wishlist две сортировки, и они различаются только ключом:

sortКлючОткуда значения ключа
createdAt(created_at, id), descколонки строки
occasionDate(группа, расстояние в днях, id), ascвычисляются из occasion_date и asOf — «сегодня» на момент первой страницы

Шаги «отрезать после курсора, упорядочить, взять limit + 1, собрать курсор» одинаковы. Их пишут один раз в keyset.ts. Сортировка становится описанием (пресетом): направление, ключ над колонками, тот же ключ над значениями курсора, как построить курсор из строки.

asOf показывает, зачем в описании есть параметры. На первой странице это «сегодня», дальше его берут из курсора. Иначе после полуночи посреди листания Wishlist «на сегодня» переедет из будущих в прошедшие, и строки пропадут или повторятся.

Решение ревью 2026-10-19 (design, решение 4): модуль сам владеет ORDER BY, LIMIT и OFFSET и очищает чужие. Ключ пресета не может быть пустым, а длины двух ключей сверяются.

5. Проверь себя: порядок обработки запроса страницы

Собери шаги обработки GET /api/wishlists?limit=2&cursor=… в порядке выполнения. Две строки лишние.

  • PostgreSQL возвращает до limit + 1 строк
  • SELECT COUNT(*) — узнать, есть ли следующая страница
  • query Schema декодирует cursor в { createdAt: Date, id } или отвечает 400
  • первые limit строк → items, курсор последней из них → nextCursor
  • проверить Session, иначе 401
  • OFFSET (номер страницы − 1) × limit
  • applyKeyset: WHERE (ключ) < (курсор), ORDER BY ключ, LIMIT limit + 1
  • repository: WHERE owner_id = viewerId

Сначала Session, потом разбор query (design, решение 6): без Session ответ 401 при любом query. Область видимости задаёт repository, keyset дописывает своё к его запросу. COUNT не нужен: следующую страницу выдаёт лишняя строка. OFFSET отсутствует по определению keyset.

7. Маршрут: от конкретного к общему

Модуль не пишется сразу обобщённым. Сначала работающая конкретная функция, потом из неё вынимается общее, и тесты остаются те же.

  1. Конкретная функция. Одна страница Wishlist по createdAt без обобщений, как listSessions в уроке 0010, и твой тест на PostgreSQL. Готово, когда тест обходит 5 строк по 2.
  2. Вынуть общее. Что в функции зависит от сортировки, уходит в описание пресета, остальное становится applyKeyset и toPage. Готово, когда тот же тест зелёный и в общем коде нет слова createdAt.
  3. Защиты из ревью. Очистка чужих ORDER BY и OFFSET, непустые ключи, сверка длин. Каждое правило начинается с падающего теста.
  4. Вычисляемый ключ occasionDate (4.2), потом endpoint (5) и property-тест (6.1).
