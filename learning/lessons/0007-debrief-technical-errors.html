1. Одна и та же ошибка хэша — разные причины в signup и login

Чтоauth.service.ts:119–142:

// mapSignupError: хэш только что посчитан — ошибка кода
Match.tag('PasswordHashIntegrityError', (cause) => new AuthInternalError({ cause })),
// mapLoginError: хэш прочитан из базы — запись повреждена
Match.tag('PasswordHashIntegrityError', (cause) => new AuthDataIntegrityError({ cause })),

ПочемуКлиент в обоих случаях получает 500. Разница — поле reason в строке лога operation.failed. Всплеск dataIntegrity значит «в базе битые строки, нужна починка данных». Всплеск internal значит «ошибка в коде, нужен разработчик». Если оба случая слить в internal, по логу их не различить.

ЦенаЕщё один тег в объединениях AuthSignupError, AuthLoginError, AuthAuthenticateError. Каждый catchTags технических ошибок обязан перечислить три тега, а не два.

Сохранённый хэш пароля не разбирается: login получил PasswordHashIntegrityError. Какой reason будет в логе и какой статус у ответа? А если та же ошибка случится при signup?

Login: dataIntegrity, 500. Signup: internal, 500. Решение 1.

2. isRetryableSqlFailure сначала проверяет сам SqlError

Чтоsql-failure.ts:19–32:

export const isRetryableSqlFailure = (error: unknown): boolean => {
  if (isSqlError(error)) {
    return isRetryableSqlError(error) || …;
  }
  return Predicate.hasProperty(error, 'cause') &&
    isSqlError(error.cause) && isRetryableSqlError(error.cause);
};

ПочемуФункция получает два вида ошибок. «Голый» SqlError приходит из db.withTransaction при begin и commit. Ошибка репозитория держит SqlError в cause. Но у SqlError тоже есть поле cause — это его reason, например ConnectionError. Если проверять cause первым, обрыв соединения на begin найдёт в cause не SqlError и ответит false: клиент получит 500 вместо 503. Прежняя копия в users.service.ts так и не узнавала голый SqlError.

ЦенаПравило «временный ли сбой» теперь общее для всех модулей. Его изменение (например, UnknownError на acquireConnection) сразу меняет статусы и в auth, и в users.

В isRetryableSqlFailure поменяли порядок: сначала проверка error.cause, потом isSqlError(error). Транзакция signup упала на begin с ConnectionError. Какой статус получит клиент?

500 вместо 503: в cause голого SqlError лежит ConnectionError, а не SqlError. Решение 2.

3. Ключи reasons — ровно теги технических ошибок модуля

Чтоusers.handlers.ts:17–25 и technical-failure.ts:35:

makeTechnicalFailureHandler<UsersTechnicalError>()({
  module: 'users',
  operations: UserOperation,
  reasons: { UserDataIntegrityError: 'dataIntegrity', UsersInternalError: 'internal',
             UsersUnavailableError: 'unavailable' },
});
// readonly reasons: Readonly<Record<TechnicalError['_tag'], FailureReason>>;

ПочемуРаньше ключи выводились из самого объекта, и опечатка проходила. Ошибка всплывала в catchTags непонятным сообщением про несовместимость. Теперь лишний тег даёт TS2353 прямо на строке ключа, а пропущенный — TS2741 на reasons. Обе проверки закреплены @ts-expect-error в technical-failure.test.ts.

ЦенаПустой первый вызов (): TypeScript не умеет задать один параметр типа явно, а второй вывести. Новый модуль обязан объявить тип вроде UsersTechnicalError.

В reasons модуля users написали UsersUnavailableEror: 'unavailable' вместо UsersUnavailableError. Когда и где это обнаружится?

При компиляции, до запуска: TS2353 на строке с опечаткой и TS2741 на reasons — нет ключа UsersUnavailableError. Решение 3.
