1. Доменная ошибка не знает адреса; instance подставляет middleware из пути запроса

Чтоauth.handlers.ts:137–147:

const session = yield* service.authenticate(credential).pipe(
  Effect.catchTags({
    AuthUnauthenticatedError: () =>
      Effect.gen(function* () {
        const request = yield* HttpServerRequest.HttpServerRequest;
        return yield* new AuthUnauthenticatedHttpError({
          instance: getRequestPathname(request),   // путь без query
        });

ПочемуРаньше тело 401 было схемой с instance: Schema.tag('/api/auth/me'). Пока Session проверял один /me, это работало. С POST /api/wishlists клиент получал 401 с instance: /api/auth/me — ссылкой на чужой ресурс. Полный URL вместо пути принёс бы в тело и в лог query: ?source=test сегодня, токен приглашения завтра. Семь тестов Session в Wishlist проверяют путь без query.

ЦенаAuthService больше не может отдать готовое тело 401: адрес знает только граница HTTP. Каждый защищённый маршрут отвечает одним классом AuthUnauthenticatedHttpError, а старая схема AuthUnauthenticatedProblem удалена без алиаса.

В middleware заменили getRequestPathname(request) на request.url. Клиент без cookie отправляет GET /api/wishlists/ID?source=test. Что будет в instance и что упадёт?

/api/wishlists/ID?source=test: query попадёт в тело. Падают тесты Session «… instance без query» в wishlists.handlers.test.ts. Решение 1.

2. Миграция 0004 сначала чистит имена, потом добавляет CHECK; тест стартует со схемы 0003 и грязных строк

Что0004_wishlists.ts:28–37 и wishlists.migration.test.ts:66–80:

UPDATE "public"."users"
SET "display_name" = coalesce(nullif(btrim("display_name"), ''), 'User')
WHERE "display_name" <> btrim("display_name") OR btrim("display_name") = '';
ALTER TABLE "public"."users" ADD CONSTRAINT "users_display_name_trimmed_check"
  CHECK ("display_name" = btrim("display_name") AND "display_name" <> '');
-- тест: 0001–0003, затем строки '  Ada  ', '   ', 'Ada', затем все миграции

ПочемуЕсли поменять шаги местами, ADD CONSTRAINT встретит строку ' Ada ' и PostgreSQL откажет с кодом 23514. Миграция не применится, запуск сервера остановится. На пустой тестовой БД этого не видно: строк нет, CHECK добавляется. Поэтому тест сначала применяет только 0001–0003, вставляет три грязных имени и ждёт 'User', 'Ada', 'Ada'. Отказ новой записи ' Bob ' он сверяет по коду 23514 и имени ограничения, а не по факту «что-то упало».

ЦенаМиграция молча меняет данные: имя ' ' становится 'User'. Обратных миграций нет, исходное значение не вернуть.

В 0004 поменяли местами UPDATE и ADD CONSTRAINT. На локальной БД есть User с display_name = ' Ada '. Что произойдёт при запуске миграций и какой тест это поймает?

PostgreSQL отклонит ADD CONSTRAINT с 23514, миграция упадёт. Поймает тест «normalizes existing display names before adding the trimmed check»: он воспроизводит ровно такую БД. Решение 2.

3. Occasion Date остаётся строкой от драйвера до JSON

Чтоpg-date.test.ts:7–9 и .kysely-codegenrc.json:

// @effect/sql-pg 4.0.4 читает `date` своим кодеком и отдаёт строку YYYY-MM-DD.
// Тест упадёт, если дата начнёт приходить объектом Date или сдвигаться
// вместе с часовым поясом процесса.
"dateParser": "string"     // generated: occasionDate: string | null

ПочемуDate — это момент времени, а у 2028-02-29 времени нет. Если превратить дату в Date по полуночи процесса, в TZ=Europe/Moscow получится 2028-02-28T21:00:00Z. Обратное форматирование по UTC вернёт 2028-02-28: клиент создал 29 февраля, а прочитал 28-е. Строка не зависит от пояса: pg-date.test.ts гоняет один и тот же круг в UTC, Москве и Лос-Анджелесе. В rc.108 для этого добавляли pg.TypeOverrides; в 4.0.4 у sql-pg свой протокол без pg, и такая настройка лишняя.

ЦенаСравнение дат — строковое: окно проверяет value >= min. Это верно только для формата YYYY-MM-DD с ведущими нулями, поэтому Schema отклоняет 2028-2-9. Обновление @effect/sql-pg может сменить кодек — тогда первым упадёт pg-date.test.ts.

Кто-то разбирает date в Date по полуночи процесса, а в ответе пишет toISOString().slice(0, 10). Сервер работает с TZ=Europe/Moscow, клиент создал Wishlist с 2028-02-29. Что вернёт GET?

2028-02-28: полночь по Москве — это 21:00 предыдущего дня по UTC. Решение 3.
