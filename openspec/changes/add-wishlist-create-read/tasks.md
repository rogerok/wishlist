Это проверяет сценарии «Вчера принимается» и «Вчера минус один день отклоняется» и чтение Clock на каждом decode. Если HttpApi не выполняет эффектную проверку, сохранить наблюдение, выбрать разрешённый планом запасной путь service/Clock с кодом `WISHLIST_OCCASION_DATE_OUT_OF_RANGE` и удалить неработающую проверку из payload. После выбора пути обновить delta-spec: в требовании окна и обоих сценариях отказа оставить только выбранный код 400 и удалить проигравшую ветку кода ошибки. Для основного пути сохранить контракт единственной записи `errors` с `location: "payload"`, `path: ["occasionDate"]` и `message` с обеими границами окна. Не объявлять поддержку checkEffect доказанной при зелёном тесте только прямого decode. Доказательство основного пути: `pnpm --filter @wishlist/api test src/modules/wishlists/schemas/create-wishlist.payload.test.ts` и `openspec validate add-wishlist-create-read --strict` проходят; при запасном пути задача закрывается после реализации service в 3.1 и зелёного HTTP-теста выбранного контракта в 3.3.

## 3. Шаг 3.3 — create/read с Session

- [ ] 3.1 Реализовать `WishlistRepository`, `WishlistService` и `WishlistModuleLive` с actor отдельным аргументом. INSERT явно задаёт четыре нормализованных поля и владельца; SELECT использует `id AND (owner_id = viewerId OR visibility = public)`. Repository декодирует строки без нормализации и переводит технические отказы в `OperationFailed` через существующие `sqlOperationFailed` и `invalidRecordFailed`; service пропускает их. При основном пути service не проверяет окно; при выбранном в 1.1 запасном пути create проверяет его через Clock и выдаёт собственную типизированную ошибку 400. Read окно не проверяет ни при одном пути.
