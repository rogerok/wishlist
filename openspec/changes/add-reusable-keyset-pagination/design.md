# Design

## Context

Мотивация — в proposal.md, контракт — в specs, выбор keyset и формат курсора — в
[ADR-0008](../../../docs/adr/0008-keyset-pagination-with-opaque-cursor.md). Состояние кода, которое определяет подход:

- `wishlists.created_at` — `timestamptz(3)`: миллисекунды, как у JS `Date`, поэтому значение ключа проходит через
  курсор без потери точности. Равные `created_at` возможны.
- `wishlists.id` — `gen_random_uuid()` (UUIDv4): уникален, но не упорядочен по времени; годится только как
  последняя колонка ключа.
- Репозитории строят запросы Kysely через `DB` (`infra/db/db.service.ts`) и переводят отказы в `OperationFailed`
  (`sqlOperationFailed`, `invalidRecordFailed`).
- Ошибки разбора `params`/`query`/`payload` уже превращаются в 400 `REQUEST_VALIDATION_FAILED` с `location`
  (`infra/errors/request-validation.ts`); строгий разбор включён только для тела (`infra/api/api.ts`).
- Окно Occasion Date уже считает «сегодня» по UTC через `DateTime.now` и `Clock`
  (`modules/wishlists/schemas/wishlist.schema.ts`).

## Goals / Non-Goals

**Goals:**

- Один модуль, который знает самое ошибкоопасное в keyset — тай-брейкер, согласование `WHERE` с `ORDER BY`,
  `limit + 1`, сборку `nextCursor` — так, что потребитель только объявляет сортировки и пишет свою область видимости.
- Два вида ключа: из колонок и вычисляемый с параметром, который фиксируется на первой странице.
- Поведение модуля доказано property-based тестом на настоящем PostgreSQL.

**Non-Goals:**

- Ключ по колонке с `NULL` через подмену на `infinity` (решение записано в ADR-0008, реализуется с первым таким
  пресетом).
- Вынос модуля в пакет: откладывается до второго потребителя. Типы модуля уже обобщены по `DB` и таблице `TB`:
  параметр `TB` нужен, чтобы `ExpressionBuilder` пресета видел колонки таблицы запроса, а `DB` приходит вместе с ним;
  во время выполнения обобщение ничего не стоит (ревью 2026-10-19).
- Фильтры списка, страницы назад, `totalCount`.

## Decisions

### 1. Модуль в `apps/api/src/infra/pagination/`, без импортов из `#modules/*`

Модуль зависит только от `effect`, Kysely и типов `DB`. Запрет импортов из модулей держит границу, по которой его
позже вынесут в пакет. Альтернатива — пакет сразу — отложена решением владельца до второго потребителя.

### 2. Сортировка — именованный пресет, объявленный потребителем

Пресет описывает:

- упорядоченный список выражений ключа, последнее — уникальный `id`;
- одно общее направление;
- Schema значений, которые курсор хранит о последней строке;
- для вычисляемого ключа — Schema параметров и `Effect`, вычисляющий их для первой страницы.

Набор пресетов списка — запись `имя → пресет`. Из него модуль выводит Schema `sort` (литералы имён) и Schema курсора
(объединение по тегу `sort`).

Schema значений курсора обязана принимать только значения, которые PostgreSQL примет в параметре запроса. Курсор
приходит от клиента и может быть подделан, а отказ PostgreSQL (`22P02 invalid_text_representation`,
`22008 datetime_field_overflow`) `sqlOperationFailed` превратит в 500. Для Wishlist:

| Поле курсора           | Schema                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| `id`                   | `WishlistIdSchema`                                                                                            |
| `createdAt`            | `PgInstantFromString`: строка ровно `YYYY-MM-DDTHH:mm:ss.sssZ`, существующий момент, год `0001–9999` → `Date` |
| `asOf`, `occasionDate` | `PgCalendarDate`; `occasionDate` ещё и `null`                                                                 |

`CalendarDate` сейчас пропускает `0000-01-01` (в JS это валидный год), поэтому в `infra/schemas/dates.schema.ts`
появляются отдельные Schema `PgCalendarDate` (`CalendarDate` с годом от `0001`) и `PgInstantFromString` (момент
`createdAt`). Сам `CalendarDate` не меняется: `wishlist.schema.test.ts` ждёт для `0000-01-01` сообщение окна create, а
граница года в `CalendarDate` подменила бы его календарным.

Альтернатива: модуль только кодирует курсор, а `WHERE` и `ORDER BY` пишет репозиторий. Отклонена: тогда каждый
потребитель повторяет согласование знака сравнения с направлением, `limit + 1` и сборку курсора.

### 3. Курсор — цепочка Schema

Цепочка: base64url-строка → JSON-строка → объединение `TaggedStruct` по `sort` с полями ключа и параметрами пресета.
Используются `Schema.StringFromBase64Url` и `Schema.fromJsonString`, точные имена проверяются по типам 4.0.4. Тот же
кодек кодирует `nextCursor`, поэтому формат описан в одном месте и симметричен.

Query-Schema списка — структура `sort`, `cursor`, `limit`. Модуль даёт детали (`makeCursorCodec`, `LimitQueryParam`,
`cursorMatchesSort`), а Struct собирает потребитель. Обобщённую фабрику Struct Effect 4.0.4 не типизирует:
`Schema.Literals` от параметра типа теряет литералы, а фильтр на уровне структуры с полями-параметрами не видит
`sort` и `cursor` (наблюдение 2026-10-19). Сборка из конкретных Schema типизируется и занимает несколько строк:

- `sort` и `limit` получают значения по умолчанию при декодировании (`withDecodingDefault*`). ADR-0007 касается тела
  запроса, а не query, см. ADR-0008;
- `limit` — строка по шаблону `^[1-9][0-9]*$`, затем число в диапазоне `1..100`. `NumberFromString` не подходит: он
  декодирует через `Number()` и пропускает `0x10`, `1e1` и `" 5"`;
- проверка на уровне структуры сравнивает `cursor.sort` с `sort`.

Все отказы — ошибки Schema, поэтому их без нового кода превращает в 400 существующий middleware валидации. Любая
ошибка декодирования query, включая проверку на уровне структуры, оборачивается в `HttpApiSchemaError.wrap("Query", …)`
(`HttpApiBuilder.ts:876`) и получает `location: "query"`.

Наблюдение задачи 1.2 (`infra/pagination/query-errors.test.ts`, 2026-10-18):

| Отказ query                                                    | `path` в записи `errors` |
| -------------------------------------------------------------- | ------------------------ |
| неизвестный ключ `zz`                                          | `["zz"]`                 |
| фильтр на уровне структуры возвращает строку                   | `[]`                     |
| фильтр на уровне структуры возвращает `{ path: ["b"], issue }` | `["b"]`                  |

Поэтому проверка «`cursor.sort` равен `sort`» возвращает `{ path: ["cursor"], issue }`: клиент видит, что виноват
курсор, а не корень query.
Повторённый ключ (`?limit=1&limit=2`) HttpApi передаёт массивом (`Schema.toCodecArrayFromSingle`), и Schema строки
его отклоняет.

Альтернатива — отдельная типизированная ошибка `InvalidCursor` с собственным кодом. Отклонена решением владельца:
клиент обрабатывает её так же, как любой невалидный query.

### 4. SQL: сравнение строк значений в одном направлении

Для пресета с ключом `(k1, …, kn)` и направлением `desc` модуль добавляет к запросу потребителя три части:

- `WHERE (k1, …, kn) < (v1, …, vn)`, если курсор есть;
- `ORDER BY k1 desc, …, kn desc`;
- `LIMIT limit + 1`.

Для `asc` знак сравнения меняется на `>`. Сборка страницы берёт первые `limit` строк. Если строк пришло больше,
`nextCursor` кодирует значения ключа **последней из `limit` выданных строк**, а не `limit + 1`-й. Курсор по
`limit + 1`-й строке — классическая ошибка keyset: эта строка не попадает ни на одну страницу. Если строк не больше
`limit`, `nextCursor` равен `null`.

Сравнение строк значений с одним направлением PostgreSQL выполняет как переход по составному индексу. Смешанные
направления потребовали бы развёртки в `OR`, которую индекс так не использует; поэтому одно направление на пресет.

**Модуль владеет порядком и размером выборки.** Kysely `orderBy` добавляет сортировку к уже объявленной, а `offset`
сохраняется. Ревью 2026-10-19 наблюдало запрос потребителя с `orderBy('title')` и `offset(5)`:
`order by "title" asc, "createdAt" desc, "id" desc limit $1 offset $2` — первичный порядок задаёт `title`, курсор
описывает `(createdAt, id)`, а `OFFSET` пропускает строки после курсора. Поэтому `applyKeyset` перед своими частями
очищает `ORDER BY`, `LIMIT` и `OFFSET` запроса (`clearOrderBy`, `clearLimit`, `clearOffset`). `WHERE` потребителя —
область видимости, например `owner_id = viewerId`, — сохраняется. Отклонённые варианты (решение владельца
2026-10-19): только предусловие в комментарии — некорректный запрос остаётся возможным; отказ при найденной сортировке
через `toOperationNode()` — зависимость от формы AST Kysely и ошибка только во время выполнения.

**Контракт ключа.** Пресет задаёт ключ дважды: над колонками строки (`rowKey`) и над значениями курсора
(`cursorKey`). Пресет обязан соблюдать:

1. одинаковое число компонентов и одинаковый их порядок в обоих ключах;
2. совместимые SQL-типы компонентов на одной позиции;
3. отсутствие SQL `NULL` в итоговом ключе: сравнение кортежей с `NULL` в решающей позиции даёт неизвестный результат,
   и `WHERE` исключает строку;
4. уникальность полного ключа среди строк результата; последний компонент — уникальный `id`.

Защита — простые ограничения и проверка поведения, а не система типов (решение владельца 2026-10-19):

- оба ключа имеют тип `Array.NonEmptyReadonlyArray<Expression<unknown>>`, пустой ключ не компилируется;
- `applyKeyset` сверяет длины ключа строки и ключа курсора; несовпадение — дефект кода, падение, видимое на первом
  тесте;
- вычисляемый пресет пишет общие функции выражений и применяет их к обеим сторонам (решение 5);
- пункты 2–4 и порядок проверяет обход на PostgreSQL (задача 6.1).

Отклонён один источник ключа, из которого модуль сам строит обе стороны: требует сложной обобщённой типизации над
Kysely (решение 3, Risks), а совпадение порядка всё равно доказывает только обход на PostgreSQL.

### 5. Пресет `occasionDate`: вычисляемый ключ относительно `asOf`

Ключ — три выражения, все по возрастанию:

| Выражение     | Значение                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `bucket(d)`   | `0`, если `d >= asOf`; `1`, если `d < asOf`; `2`, если `d IS NULL`                                            |
| `distance(d)` | `d - asOf` для группы 0, `asOf - d` для группы 1, `0` для группы 2 (разность `date` в PostgreSQL — целые дни) |
| `id`          | тай-брейкер                                                                                                   |

Курсор хранит `asOf`, `occasionDate` и `id` последней строки. Значения для сравнения в `WHERE` модуль получает,
применяя **те же** функции выражений к параметрам курсора. Правило группы существует в одном месте, а в кортеже
сравнения нет `NULL`.

Каждый параметр внутри выражения ключа явно приводится к типу: `$n::date` для `asOf` и `occasionDate`, `$n::uuid` для
`id`. Без приведения `CASE WHEN $2 IS NULL … WHEN $2 >= $3 …` не даёт PostgreSQL вывести тип, и запрос падает с
`could not determine data type of parameter $2`. Наблюдение на локальном PostgreSQL 16.3 через `PREPARE`, 2026-10-18:
без приведения — `could not determine data type of parameter $1`, с `::date` запрос выполняется. Тип параметра
выводит сервер, поэтому драйвер (`@effect/sql-pg` → postgres.js) на это не влияет; задача 4.2 пройдёт через
настоящий драйвер уже с приведением.

`asOf` для первой страницы вычисляет `Effect` пресета: `DateTime.now` → начало дня UTC → `formatIsoDateUtc`, как в
окне Occasion Date. `Clock` — сервис по умолчанию, поэтому слой (Layer) не нужен, а тесты управляют временем через
`TestClock`. На следующих страницах `asOf` берётся из курсора (ADR-0008, вариант «вычислять на каждой странице»
отклонён).

### 6. Строгий query на уровне API

`AppApi` получает `.annotate(HttpApi.QueryParseOptions, requestParseOptions)` рядом с `PayloadParseOptions`.
Аннотация действует только на маршруты с query-Schema: без неё HttpApi query не декодирует (`HttpApiBuilder.ts:844`,
`:875`). Поэтому `POST /api/wishlists?ownerId=…` по-прежнему отвечает 201, что и закрепляет существующий тест.
Задача 1.1 остаётся регрессионной проверкой этого факта.

Порядок обработки задан кодом: декодирование params, headers, query и payload выполняется внутри `applyMiddleware`
(`HttpApiBuilder.ts:854–876`), а `SessionAuthentication` подключён к группе Wishlist. Без действующей Session ответ —
401 при любом query, и ошибки валидации до аутентификации не раскрываются. Сценарий «Невалидный query без действующей
Session» закрепляет этот порядок против будущей перестановки middleware.

### 7. Индекс

Миграция `0005`:

- создаёт `wishlists_owner_id_created_at_id_idx` на `(owner_id, created_at DESC, id DESC)`;
- удаляет `wishlists_owner_id_idx`.

Новый индекс начинается с `owner_id`, поэтому покрывает и выборки по владельцу, и каскадное удаление User.
Миграция только вперёд (решение владельца). Для `occasionDate` отдельный индекс бесполезен: ключ зависит от параметра
запроса.

### 8. Возможности Effect в тестах

- **`Stream.paginate`** превращает «запрос страницы по курсору» в поток элементов и собирает полный обход.
- **`Order`** формально задаёт ожидаемый порядок пресета (`Order.combine` по полям) — независимый от SQL оракул. Он
  живёт в тестовом файле, а не в пресете: иначе в production-коде появится второе описание порядка, нужное только
  тесту, и оракул перестанет быть независимым.
- **Property-based тест** через установленную интеграцию `effect/testing` и fast-check на настоящем PostgreSQL:
  - генератор выдаёт 0–30 строк, `created_at` из 3 значений (чтобы были равные), Occasion Date из небольшого набора
    вокруг `asOf` и `null`, `limit` в диапазоне `1..5`;
  - свойство: обход потоком равен `Array.sort(rows, order)` и не содержит повторов.

  Число прогонов ограничено, чтобы не упираться в таймаут контейнера.

## Risks / Trade-offs

- [Пресет `occasionDate` не переходит по индексу] → PostgreSQL сортирует все Wishlist владельца на каждой странице.
  Приемлемо для десятков и сотен; пересмотреть, если у владельца появятся тысячи.
- [Подделанный курсор доходит до PostgreSQL] → строгие Schema значений (решение 2) и матрица «Курсор правильной формы
  с недопустимым значением» в тестах.
- [Обобщённая типизация ссылок на колонки Kysely сложна] → ключ типизирован как `Expression<unknown>`; если тип
  выражения не выводится, допускается узкое явное объявление типа значения ключа в пресете вместо `any`.
- [Пресет нарушает контракт ключа, а типы это пропускают: переставлены компоненты одного SQL-типа, `NULL` в ключе,
  неуникальный ключ] → строки молча пропускаются или повторяются. Ловит только обход на PostgreSQL для каждого
  пресета (задача 6.1); сверка длин в `applyKeyset` ловит лишь разное число компонентов.
- [Миграция `0005` строит индекс без `CONCURRENTLY`] → `CREATE INDEX` держит блокировку `SHARE`, и запись в
  `wishlists` ждёт до конца построения; `DROP INDEX` кратко берёт `ACCESS EXCLUSIVE`. `CONCURRENTLY` невозможен:
  `PgMigrator` выполняет миграцию в транзакции. При текущем объёме данных принято; для большой таблицы нужна миграция
  вне транзакции.
- [Property-тест с контейнером медленный и иногда падает по таймауту 5 с (STATE.md)] → ограниченное число прогонов,
  общий контейнер на файл, увеличенный таймаут только для этого файла.
- [Изменение точности `created_at`] → если колонка станет `timestamptz(6)`, курсор через JS `Date` потеряет
  микросекунды, и появятся пропуски. Тест равных `createdAt` на границе страниц это ловит.

## Migration Plan

`0005` создаёт новый индекс и удаляет старый в одной миграции; данные не меняются. Отката нет: миграции только вперёд.
