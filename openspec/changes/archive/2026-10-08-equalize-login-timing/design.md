# Design

## Context

`login` в `auth.service.ts` возвращает `AuthInvalidCredentialsError` без вызова `hasher.verify`, когда
`usersRepo.getByEmail` или `passwordRepo.getByUserId` вернули `Option.none()`. `hasher.verify` разбирает сохранённый хэш
и запускает scrypt — ~300 мс.

## Decisions

### Закрыть только канал времени в login

Отказ от этапа P0 целиком: ответ signup без 409 требует подтверждения
email, это несколько недель работы. Отказ от переноса: утечка не зависит от остального P0 и закрывается одним тестом.

### Фиктивный хэш считается при сборке AuthService

`AuthServiceLive` один раз вызывает `hasher.hash` с постоянной строкой и хранит результат. Строка не секретна: без User
login отказывает даже при совпадении с ней.

- **Константа в коде.** Отклонено: после смены параметров scrypt в `constants.ts` константа перестанет разбираться.
  Тогда каждый login с неизвестным email получит `PasswordHashIntegrityError`, а значит 500 вместо 401.
- **`Effect.cached` при первом login.** Отклонено: `Effect.cached` запоминает и ошибку. Проверено 2026-10-08: после
  первой ошибки второй вызов вернул ту же ошибку, а расчёт выполнился 1 раз. Перегрузка hasher в первом запросе
  навсегда сломала бы login с неизвестным email.

Цена выбранного варианта: запуск API дольше на ~300 мс, и ошибка `hasher.hash` останавливает запуск.

### Одна проверка пароля до развилки

`login` вызывает `hasher.verify` один раз, до проверки, найдены ли User и Password Credential. Хэш для проверки —
настоящий из Password Credential или, если его нет, фиктивный.

Выбор владельца, вместо двух вызовов в разных ветках: один вызов `verify` стоит до развилки, поэтому любая дорога
проходит ровно одну проверку. С двумя вызовами это держится на дисциплине: копии могут разойтись. Так и случилось при
переходе на один вызов: в ветке отказа остался старый `verify`, и неизвестный email проходил 2 проверки вместо 1 — тест
показал `[ false, false ]`.

### Результат фиктивной проверки не влияет на ответ

Ответ — всегда `AuthInvalidCredentialsError`, даже если `verify` вернул `true`. Ошибки `verify`
(`PasswordHashOverloadedError`, `SecurePrimitiveUnavailableError`) проходят дальше так же, как при проверке настоящего
хэша: под перегрузкой оба запроса получают 503.

## Risks

- Время выравнивается только для scrypt. Запрос `passwordRepo.getByUserId` для существующего User остаётся лишним
  обращением к БД — единицы миллисекунд против сотен у scrypt.
- Тесты считают проверки пароля только для неизвестного email и User без Password Credential. Лишняя проверка на дороге
  «неверный пароль» удвоила бы время отказа, и ни один тест этого не заметит.
